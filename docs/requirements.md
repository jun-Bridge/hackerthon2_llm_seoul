> 이 문서는 **WHAT의 단일 진실원천**이다. 결정의 *이유*와 과정은 `dev-log.md`.

## 1. 목적 (한 문장)
대화하면서 LLM과 함께 문서를 만들어 나가는 웹 서비스 — **LLM은 함수 호출로 캔버스 문서를 읽고 쓰기만 하고(소유하지 않고), 사용자는 같은 문서를 언제든 직접 편집한다.**

## 2. 사용자·이해관계자
- **주 사용자**: 개인 사용자. 로그인 후 자기 세션과 문서만 본다. 공유·협업 없음.
- **이해관계자**: 해커톤 팀(구현), 심사(데모).
- 다중 사용자가 같은 문서를 동시에 보는 상황은 없다.

## 3. 범위
### In scope
- **자체 계정 시스템** — 가입·로그인·로그아웃·세션 유지. 소셜 로그인 없음.
- **채팅 세션 관리** — 새 세션 생성, 현재 대화, 과거 대화 목록, 세션별 주제(제목 자동 생성)
- **세션 컨테이너** — 대화 상태를 Redis에 두고 요청마다 복원. 버퍼가 차면 요약(absorb)으로 압축.
- **동시 접속 차단** — 한 계정은 한 환경에서만. 이미 열려 있는 세션에 다른 곳에서 접근하면 잠금 표시.
- **텍스트 대화** — 스트리밍 응답
- **캔버스 문서** — 세션에 딸린 문서 하나(세션당 정확히 1개). **마크다운, 줄 단위 블록.** LLM이 **함수(tool call)로 읽고 제안한다.**
- **문서 작업** — 다운로드(.md), 복사·잘라내기·붙여넣기, 실행취소·다시실행. 편집기로서 최소한 갖춰야 할 것들.
- **일괄 서식 버튼** — 버튼 하나로 LLM이 문서 전체를 읽고 마크다운 서식을 **일괄 제거**하거나 **적절히 적용**해 편집한다.
- **사용자 직접 편집** — 사용자가 캔버스를 자유롭게 고쳐도 LLM이 다음 턴에 최신 상태를 읽는다.
- **편집 제안 · diff · 승인** — **LLM은 문서를 직접 쓰지 못한다.** 편집안을 내면 문서 코어가 현재 본문과 비교해 diff(+/−)를 보여주고, 사용자가 **적용**을 눌러야 반영된다.
- **실행취소·다시실행(undo/redo)** — 승인된 편집과 사용자 편집을 같은 스택에서 되돌린다. 서버 보관.
- **편집 잠금(세마포어)** — LLM이 편집안을 만드는 동안, 그리고 제안이 떠 있는 동안 캔버스를 블러 처리하고 사용자 편집을 잠근다.
- 로컬 개발용 컨테이너 정의(`docker/`), git 연동

### Out of scope (YAGNI — 의도적으로 쳐낸 것)
> **이 서비스는 "툴"이다.** 꾸밈·맞춤·부가 기능은 전부 없다. 텍스트 대화와 캔버스, 끝.

- **카카오톡 관련 전부** — 소셜 로그인, 카카오 API 연동. 자체 계정으로 대체.
- **팀 기능 전부** — 팀 생성·초대·공유·권한. 문서는 소유자 1인만.
- **사용자 맞춤·성향 추론 전부** — 세션 주제로 성향을 뽑거나, 사용자별로 동작을 바꾸는 것 없음. 세션은 서로 독립.
- **테마 기능** — 다크모드·색 테마 선택 없음. 한 벌로 고정.
- **이미지 전부** — 업로드·표시·생성 없음. 텍스트만.
- **세션 간 크로스 참조** — 한 세션이 다른 세션의 내용을 알지 못한다.
- 화려한 UI. 텍스트 대화 + 캔버스, 그 이상 없음.
- **AWS 프로비저닝·배포·업로드 — Kiro IDE에서 별도 처리.** 이 레포는 개발 + git까지.
- **파일 업로드·RAG** — 이번 범위 밖. 넣을지는 슬롯 10에서 판단.
- **회원 탈퇴·비밀번호 재설정** — 이번 범위 밖. 계정은 가입·로그인·로그아웃까지.

## 4. 핵심 유스케이스
1. **가입·로그인** — 자체 계정으로 가입하고 로그인한다. 이후 요청은 로그인 상태로 인증된다.
2. **새 세션 시작** — 새 대화를 연다. 첫 대화가 오가면 세션에 주제(제목)가 붙는다.
3. **과거 세션 이어가기** — 목록에서 과거 세션을 골라 열면 그 대화와 그 문서가 그대로 복원된다.
4. **LLM이 편집을 제안한다** — 대화 중 "정리해줘"류 요청에 LLM이 편집 함수를 호출한다. 캔버스에 **diff가 뜬다**(추가 `+`, 삭제 `−`). 사용자가 **적용**을 누르면 그때 문서가 바뀐다. **취소**를 누르면 문서는 그대로다.
5. **사용자가 직접 고친다** — 캔버스에서 사용자가 문단을 수정·추가·삭제한다. 저장된다.
6. **LLM이 사용자 편집분을 반영한다** — 사용자가 고친 뒤 "이거 더 다듬어줘"라고 하면, LLM이 읽기 함수로 **최신 본문**을 가져와 작업한다. (LLM이 문서를 컨텍스트에 들고 있지 않으므로 stale해지지 않는다.)
7. **부분 수정** — "세 번째 문단만 짧게"에 LLM이 해당 블록만 바꾸는 제안을 내고, diff에도 그 블록만 나타난다.
7-1. **되돌리기** — 적용한 편집이 마음에 안 들면 실행취소로 직전 상태로 돌아간다. 다시실행으로 복구한다.
8. **세션 관리** — 세션 이름 변경·삭제.
9. **일괄 서식** — 사용자가 "서식 제거" 버튼을 누르면 LLM이 문서 전체를 읽고 마크다운 문법을 걷어낸 평문으로 바꾼다. "서식 적용"을 누르면 반대로 제목·목록·강조를 적절히 넣어 정리한다. 둘 다 대화 없이 버튼 한 번으로 끝난다.

## 5. 비기능 제약
- **LLM tool calling 필수** — 캔버스 전체가 함수 호출 위에 서 있다. gpt-oss-120b가 이를 지원하는지 **빌드 전 실측 확인**(슬롯 9 리스크).
- **응답 스트리밍** — 토큰 단위로 도착. tool call 진행 중에도 사용자가 상태를 본다.
- **세션 독립** — 세션 간 데이터가 섞이지 않는다.
- **인가** — 모든 세션·문서 접근은 소유자 확인을 거친다. 남의 id를 넣어도 못 본다.
- **단일 환경 접속** — 한 계정은 한 곳에서만 접속한다. 같은 문서를 두 화면이 각자 편집해 작업본이 엉키는 상황을 원천 차단한다.
- **승인 없는 변경 없음** — LLM의 어떤 도구 호출도 사용자 승인 없이 문서를 바꾸지 못한다.
- **편집 잠금** — LLM 편집안 생성 중과 제안 대기 중에 사용자 편집이 잠긴다. 잠금은 반드시 풀린다 — 응답 실패·연결 끊김에도 영구 잠기지 않아야 한다(TTL 필요).
- **시크릿은 `.env`만.** 비밀번호는 해시 저장(평문 금지).
- **모든 루프에 상한이 있다** — 한 턴의 도구 호출 횟수, undo 스택 깊이, absorb 재시도. 상한 없는 반복을 두지 않는다.
- 해커톤 기간 내 구현 가능할 것 — 애매하면 기능을 쳐낸다.

## 6. 아키텍처 — 두 개의 코어와 하나의 조율자

백엔드는 세 덩어리다. **두 코어는 서로를 모르고**, 둘을 아는 것은 **오케스트레이터** 하나뿐이다.

```
                  ┌──────────────────────────────┐
                  │        오케스트레이터         │
                  │        (턴 실행기)            │
                  │  · 한 턴의 수명 관리          │
                  │  · 도구 호출 루프 (상한 있음) │
                  │  · 잠금 획득/해제             │
                  │  · 플러시 트리거              │
                  │  · SSE 이벤트 발행            │
                  └───┬───────────┬───────────┬──┘
                      │           │           │
          ┌───────────▼──┐  ┌─────▼──────┐  ┌─▼──────────┐
          │  대화 코어    │  │ 문서 코어   │  │ LLM 클라이언트│
          │(세션 컨테이너)│  │ (캔버스)    │  │            │
          ├──────────────┤  ├────────────┤  ├────────────┤
          │ 메시지 버퍼   │  │ 줄 목록     │  │ stream     │
          │ context 요약  │  │ 제안 버퍼   │  │ tool calls │
          │ title/absorb │  │ undo/redo  │  │            │
          │ Redis 작업본  │  │ 잠금        │  │            │
          │ → PG 플러시   │  │ Redis 작업본│  │            │
          │              │  │ → PG 플러시 │  │            │
          └──────────────┘  └────────────┘  └────────────┘
                  ▲                ▲
                  └── 서로 모른다 ──┘
```

**왜 조율자를 따로 두는가**: 두 코어가 서로를 부르기 시작하면 순환이 생기고,
"승인 결과를 대화에 기록"·"일괄 서식이 LLM을 호출" 같은 걸침 동작이 어느 코어에 속하는지 매번 다투게 된다.
걸치는 일은 전부 오케스트레이터가 갖는다. 코어는 자기 것만 안다.

- **대화 코어**는 문서를 들고 있지 않다. 알고 싶으면 도구를 호출한다(오케스트레이터가 중계).
- **문서 코어**는 대화를 모른다. 줄을 다루고 잠금·제안·이력을 관리할 뿐이다.
- 둘을 잇는 유일한 통로가 **tool call**이고, 그 통로를 오케스트레이터가 쥔다. 이 경계가 "사용자가 자유롭게 편집해도 stale해지지 않는" 성질을 만든다.
- **오케스트레이터가 갖는 일** — 턴 수명, 도구 호출 루프와 그 상한, 잠금 획득·해제, 플러시 트리거, SSE 이벤트 발행, 승인 결과를 대화에 기록, 일괄 서식 실행.
- 사용자의 직접 편집도 같은 문서 코어를 통과한다 — LLM이 쓰든 사람이 쓰든 경로가 하나다.
- **LLM에게는 쓰기 권한이 없다.** 도구 호출은 제안일 뿐이고, 문서를 실제로 바꾸는 것은 사용자의 승인이다.
- **두 코어의 저장 방식이 같다**: Redis에 작업 사본을 두고 거기서 편집하다가, 트리거가 걸릴 때마다 Postgres에 통째로 덧씌운다. 상주 객체 없이 요청마다 Redis에서 복원한다.

## 7. 데이터·계약

### PostgreSQL
```
user ──< session ──< message
              └──── document ──< block
```
- `user` — id, email, password_hash, created_at
- `session` — id, user_id, title(주제), created_at, updated_at
- `message` — id, session_id, role(`user` | `assistant` | `system`), content, created_at
  - 제안의 적용/거절 결과는 `system` role 메시지로 남긴다. 다음 턴 컨텍스트에 그대로 실린다.
- `document` — id, session_id. **세션당 정확히 하나.** 세션 생성 시 함께 만들어진다. updated_at
- `block` — id, document_id, order, content, updated_at
  - **블록 = 마크다운 한 줄.** 빈 줄도 블록이다(마크다운에서 문단을 가르므로 의미가 있다).
  - 문서 전체 = 블록을 `order` 순으로 개행 이어붙인 마크다운.
  - **줄 단위인 이유**: diff의 단위와 편집의 단위가 같아진다. `+`/`−` 표시가 곧 블록 하나의 추가·삭제라 diff 계산·표시·되돌리기가 같은 좌표계 위에서 돈다.
  - **id로 가리키는 이유**: 줄 번호나 문자 offset으로 가리키면 사용자가 한 줄만 넣어도 전부 밀린다. 안정적인 id라야 자유 편집과 LLM 수정이 공존한다.
  - **`order` 재정렬**: 작업본(Redis)에서는 리스트 순서가 곧 order다. Postgres 플러시 때 0부터 다시 매긴다. 삽입할 때마다 뒤를 미는 연산은 하지 않는다.

**잠금은 Postgres에 두지 않는다.** 잠금·제안·이력은 전부 휘발성이므로 Redis가 유일한 진실원천이다.
Postgres에는 확정된 본문만 남는다.

### 캔버스 함수 (LLM tool 정의)
LLM에 노출되는 도구. **LLM은 문서를 컨텍스트에 소유하지 않고, 필요할 때 호출해서 읽는다.**
**읽기 — 즉시 실행**
- `read_document()` → 블록 목록 `[{id, order, content}]`. 항상 최신 작업본을 돌려준다.

**쓰기 — 제안만 쌓인다. 문서는 바뀌지 않는다.** (단위: 줄)
- `propose_replace_line(block_id, text)` — 그 줄을 다른 텍스트로
- `propose_insert_lines(after_block_id | null, texts[])` — 뒤에 여러 줄 삽입 (null이면 맨 앞)
- `propose_delete_lines(block_ids[])`
- `propose_replace_document(lines[])` — 전체 재작성 제안 (초안 생성·일괄 서식)

### 한 턴의 실행 흐름 (오케스트레이터)
```
사용자 메시지 도착
  → 대화 코어에서 컨텍스트 조립 (버퍼 + context 요약 + 직전 제안 처리 결과)
  → LLM 스트리밍 시작 ──────────────► SSE: token
  → 도구 호출이 오면:
       read_document  → 문서 코어에 질의, 결과를 LLM에 반환 (즉시)
       propose_*      → 문서 코어의 제안 버퍼에 적재
                        (첫 propose에서 문서 잠금) ──► SSE: lock
       ※ 도구 호출 루프에는 턴당 상한이 있다. 넘으면 강제 종료하고 그때까지의 제안을 확정 제출한다.
  → LLM 응답 종료
  → 제안이 있으면 diff 계산 ─────────► SSE: proposal
     제안이 없으면 잠금 해제 ────────► SSE: unlock
  → 대화 코어에 턴 커밋 (absorb 판단)
  → 플러시 트리거
```

### 편집 제안 흐름
1. LLM이 쓰기 도구를 호출한다 → **제안 버퍼**(`doc:{id}:proposal`)에 쌓인다. 작업본은 그대로.
2. 턴이 끝나면 문서 코어가 **현재 문서 vs 제안 적용 결과**를 비교해 diff를 만든다.
3. 프론트가 캔버스에 diff를 표시한다 — 추가된 줄 `+`, 삭제된 줄 `−`. 블록이 곧 줄이므로 diff 단위와 문서 구조가 일치한다.
4. 사용자가 고른다.
   - **적용**: 직전 상태를 undo 스택에 push → 제안을 작업본에 반영 → redo 스택 비움 → 플러시 트리거
   - **취소**: 제안 폐기. 문서는 손대지 않는다.
5. 제안이 떠 있는 동안 문서 편집은 **잠긴다.** 그 사이 사용자가 고치면 제안이 어긋나기 때문. 적용/취소해야 풀린다.
6. 제안은 TTL을 갖는다. 사용자가 세션을 떠나 방치되면 만료 폐기된다.
7. **결과를 LLM이 안다.** 적용/거절 여부가 대화 맥락에 기록되어, 다음 턴에서 LLM이 그걸 알고 행동한다.
   거절됐는데 같은 제안을 또 내밀거나, 적용된 걸 다시 제안하는 일이 없어야 한다.
   사용자가 거절 시 짧은 사유를 남기면 그것도 함께 전달된다.

**경계 유지**: 문서 코어가 대화 코어를 부르지 않는다. accept/reject 라우트(오케스트레이터)가
문서 코어에 반영을 지시하고, 그 결과를 대화 코어에 기록한다. 두 코어는 여전히 서로를 모른다.

### 편집 이력 — 스냅샷 방식
전체 버전 관리 테이블을 두지 않고, **Redis 스냅샷 스택**으로 처리한다. 문서가 줄 목록이라 스냅샷이 가볍다.

- `doc:{id}:undo` / `doc:{id}:redo` — 줄 목록 **전체 스냅샷** 스택. 깊이 상한을 둔다.
- **LLM 편집을 적용하기 직전에 반드시 스냅샷을 남긴다.** 승인한 편집이 마음에 안 들어도 한 번에 되돌아간다.
- 되돌리기 단위 = **확정된 편집 하나**. LLM 제안 적용분과 사용자 편집 확정분이 같은 스택을 쓴다.
- 새 편집이 확정되면 redo 스택을 비운다.
- 서버(Redis) 보관 — 새로고침해도 살아 있다.

### 편집 잠금
- LLM이 편집안을 만드는 동안, 그리고 **제안이 떠 있는 동안** 잠긴다. 프론트는 블러 + 입력 차단.
- 잠금·해제는 SSE로 통지한다.
- 읽기(`read_document`)는 잠그지 않는다.
- 실패·연결 끊김에도 영구 잠기지 않도록 **TTL 자동 해제** 필수.

### SSE 이벤트 계약
채널은 **세션 단위 하나**(`GET /sessions/{id}/stream`)다. 대화와 문서 이벤트가 같은 채널로 온다 —
둘은 한 턴 안에서 엮여 일어나므로 채널을 나누면 순서 보장이 깨진다.

| 이벤트 | 언제 | payload |
|---|---|---|
| `token` | LLM 응답 토큰 도착 | 텍스트 조각 |
| `tool_start` / `tool_end` | 도구 호출 시작·종료 | 도구 이름 |
| `lock` / `unlock` | 문서 잠금 상태 변경 | 사유(`llm_editing` / `proposal_pending` / `opened_elsewhere`) |
| `proposal` | 제안 준비 완료 | 제안 id, diff |
| `proposal_resolved` | 적용·거절 처리됨 | 결과, 문서 갱신본 |
| `document_changed` | 사용자 편집·undo·redo 등으로 문서가 바뀜 | 갱신본 |
| `session_meta` | title·context 갱신(absorb 결과) | 새 title |
| `turn_end` | 턴 종료 | — |
| `error` | 턴 실패 | 사유 |

**프론트 규칙**: `lock`/`unlock`을 유일한 근거로 삼지 않는다. 신호를 놓칠 수 있으므로
잠금 상태는 서버가 진실원천이고, 프론트는 잠금 중일 때 주기적으로 재확인한다.

### Redis — 두 코어의 작업본
**대화 코어**
- `session:{id}:meta` — title, context(요약), is_manual_title
- `session:{id}:buf_msgs` — 최근 메시지 버퍼
- `session:{id}:msg_count` — 사용자 메시지 누적 수

**문서 코어**
- `doc:{id}:blocks` — 블록 목록 **작업 사본.** 편집은 전부 여기서 일어난다
- `doc:{id}:dirty` — 마지막 플러시 이후 변경 여부
- `doc:{id}:proposal` — 승인 대기 중인 편집 제안 (TTL 있음)
- `doc:{id}:undo` / `doc:{id}:redo` — 스냅샷 스택
- `doc:{id}:lock` — 편집 잠금, TTL로 자동 해제

**접속 제어**
- `user:{id}:active_conn` — 계정의 현재 활성 접속
- `session:{id}:open_by` — 그 세션을 열고 있는 접속. TTL 갱신(heartbeat)으로 유지

**그 외**: 로그인 세션 · LLM 토큰 스트림 버퍼(SSE 재연결)

### 저장 모델 — Redis 작업본 → Postgres 플러시
두 코어가 같은 방식으로 돈다.

1. 요청이 오면 Redis에서 상태를 복원한다. 없으면 Postgres에서 읽어 Redis에 올린다.
2. 편집은 **Redis 작업본에만** 반영한다. 매 타건마다 DB를 때리지 않는다.
3. **트리거가 걸리면 Postgres에 통째로 덧씌운다**(플러시). 트리거:
   - LLM 턴 종료 (도구로 편집을 마친 직후)
   - 사용자 편집 후 일정 시간 무입력 (debounce)
   - 명시적 저장 · 다운로드 · 일괄 서식 실행 전후
   - 세션 이탈·종료
4. 플러시는 **전체 덮어쓰기**다. 부분 병합을 하지 않는다 — 작업본이 곧 정답이므로.

**대가**: 마지막 플러시와 Redis 유실 사이의 편집은 사라진다. 이걸 감수하는 대신 편집 반응성을 얻는다. 허용 손실 구간은 debounce 간격이 정한다(슬롯 10 미결).

### 동시 접속 차단
같은 문서를 두 화면이 각자 편집하면 Redis 작업본이 엉킨다. 두 겹으로 막는다.

1. **계정 단위 — 한 환경에서만 접속.** 로그인은 계정당 하나의 활성 접속만 허용한다.
   `user:{id}:active_conn`에 현재 접속을 기록하고, 다른 곳에서 로그인하면 기존 쪽이 밀려난다.
2. **세션 단위 — 열려 있는 세션은 잠근다.** 이미 어딘가에서 열려 있는 세션에 접근하면
   그 세션을 **블러 처리하고 "다른 곳에서 작업 중"으로 표시**한다. 읽기만 되고 편집은 막힌다.

**왜 두 겹인가**: 1번만으로는 부족하다. 밀려난 화면이 그 사실을 알기까지 시간이 걸리고,
탭 복제·새로고침으로 같은 자격증명이 잠시 둘일 수 있다. 2번은 문서에 실제로 손대는 시점에서
다시 한 번 막는 최종 방어선이다. 1번은 정책, 2번은 자물쇠.

잠금 상태는 LLM 편집 잠금과 같은 오버레이 메커니즘을 쓴다 — 블러 + 입력 차단, 사유 문구만 다르다.

### 세션 컨테이너 동작
1. **상주하지 않는다.** 요청마다 컨테이너를 새로 만들고 Redis에서 상태를 복원한다.
2. **버퍼 + 요약**: 최근 메시지 N개만 버퍼에 두고, 그보다 오래된 맥락은 `context` 문자열 하나로 압축해 들고 간다.
3. **absorb**: 버퍼가 가득 차거나 첫 메시지일 때, 별도 LLM 호출로 대화를 압축해 `title`(세션 제목)과 `context`(요약)를 새로 뽑고 **버퍼를 비운다.** 세션 제목은 여기서 자동 갱신된다.
4. **수동 제목 보호**: 사용자가 제목을 직접 정하면(`is_manual_title`) absorb가 덮어쓰지 않는다.
5. **턴 커밋**: 유저·봇 메시지를 버퍼에 넣고 저장한 뒤 absorb 필요 여부를 판단한다.
6. **문서를 소유하지 않는다.** 컨테이너는 문서 내용을 상태로 들고 있지 않다 — 필요하면 `read_document()`로 읽는다. 그래서 사용자가 문서를 아무리 고쳐도 컨테이너 상태가 stale해지지 않는다.

### 문서 작업 (문서 코어가 제공)
- **마크다운이 진실원천.** 블록 content는 마크다운 텍스트, 문서 전체는 블록을 순서대로 이은 마크다운.
- **다운로드** — 현재 문서를 `.md` 파일로 저장
- **일괄 서식 (LLM)** — 문서 전체를 읽어 서식 제거 / 서식 적용. 채팅 메시지를 거치지 않지만 **LLM 턴이므로 오케스트레이터가 실행한다**(문서 코어가 LLM을 직접 부르지 않는다). 결과는 다른 LLM 편집과 똑같이 **제안으로 뜨고 승인을 거친다.**
  **"적용" 모드의 판정은 LLM에 일임한다** — 무엇을 제목으로 올리고 무엇을 목록으로 만들지 규칙을 정하지 않는다. 사람이 diff를 보고 판단한다.
- **복사·잘라내기·붙여넣기** — 블록 단위 및 선택 텍스트 단위
- **실행취소·다시실행** — 사용자 편집 되돌리기 (LLM 수정도 되돌림 대상에 포함)
- 이 조작들은 프론트에서 즉시 반영되고 문서 코어에 반영 요청을 보낸다.

### HTTP API (초안)
- `POST /auth/signup` · `POST /auth/login` · `POST /auth/logout` · `GET /auth/me`
- `GET|POST /sessions` · `GET|PATCH|DELETE /sessions/{id}`
- `POST /sessions/{id}/messages` · `GET /sessions/{id}/stream` (SSE)
- `GET /sessions/{id}/document` — 현재 문서(줄 목록) + 잠금 상태 + 떠 있는 제안 여부
- `PATCH /documents/{id}/lines/{line_id}` — 한 줄 수정 (사용자 직접 편집)
- `POST /documents/{id}/lines` · `DELETE /documents/{id}/lines` — 줄 삽입·삭제 (붙여넣기·잘라내기)
- `GET /documents/{id}/export.md` — 다운로드
- `POST /documents/{id}/format` — body `{mode: "strip" | "apply"}`. 일괄 서식 → **제안으로 뜬다**
- `GET /documents/{id}/proposal` — 현재 떠 있는 제안과 diff
- `POST /documents/{id}/proposal/accept` · `POST /documents/{id}/proposal/reject` (body에 선택적 `reason`)
- `POST /documents/{id}/undo` · `POST /documents/{id}/redo`
- `POST /sessions/{id}/open` · `POST /sessions/{id}/heartbeat` — 세션 점유 등록·갱신 (이미 열려 있으면 읽기 전용 응답)

**공통 에러 규약**
| 코드 | 의미 |
|---|---|
| 401 | 미인증 |
| 403 | 인증됐으나 소유자가 아님 |
| 404 | 없거나 볼 권한이 없음 (열거 방지) |
| 409 | 잠금 충돌 — 문서 편집 잠금 중, 또는 세션이 다른 곳에서 열려 있음 |
| 422 | 요청 형식 오류 (존재하지 않는 `line_id` 등) |

### LLM 인터페이스
- `app/llm/base.py`의 `complete()` / `stream()` / **`stream_with_tools()`** 만 밖에 노출.
- 도구 스키마·파싱은 `app/llm/tools/`. 도구가 실제로 하는 일은 **문서 코어**(`app/document/`)가 수행하고,
  둘을 잇는 것은 오케스트레이터다. LLM 모듈이 문서 코어를 직접 import하지 않는다.
- 모델 교체는 `app/llm/` 안에서 끝나야 한다.

## 9. 수용 기준 (Acceptance — 기계검증 가능. 마일스톤별)

### M0 — 스켈레톤
- `docker compose -f docker/compose.dev.yml up`으로 postgres·redis·backend·frontend가 뜬다
- `GET /health`가 200과 함께 db·redis 연결 상태를 반환한다
- `pytest`가 0개 실패로 통과한다 (테스트 존재)

### M1 — 계정
- 가입 → 로그인 → `GET /auth/me`가 그 사용자를 반환한다 (통합 테스트)
- 잘못된 비밀번호로 로그인하면 401
- DB에 평문 비밀번호가 없다 (해시 컬럼만 존재 — 테스트로 검증)
- 로그인 없이 `/sessions` 호출 시 401
- 같은 계정으로 두 번째 로그인하면 첫 번째 접속이 무효화된다 (테스트)

### M2 — 세션·대화
- 세션 생성 후 목록에 나타난다. 다른 사용자의 세션은 목록에 없다
- 남의 세션 id로 접근 시 404 또는 403 (테스트)
- 메시지를 보내면 저장되고, SSE로 토큰이 스트리밍된다 (fake LLM으로 결정론적 검증)
- 세션 삭제 시 딸린 메시지·문서·줄이 Postgres에서 사라지고, **Redis 잔재(작업본·제안·이력·잠금·점유)도 함께 지워진다**
- 이미 열려 있는 세션에 다른 접속이 들어오면 읽기 전용으로 응답한다 (테스트)

### M3 — 문서 코어 · 캔버스 함수
- fake LLM이 쓰기 도구를 호출해도 **문서가 즉시 바뀌지 않는다.** 제안만 생긴다 (테스트)
- 제안 적용 후에야 해당 줄이 바뀌고 다른 줄은 그대로다 (테스트)
- 제안 거절 시 문서가 호출 전과 완전히 동일하다 (테스트)
- 적용/거절 결과가 다음 턴 LLM 컨텍스트에 들어간다 (테스트)
- 실행취소 후 문서가 직전 상태와 일치하고, 다시실행으로 복귀한다 (테스트)
- 새 편집이 확정되면 redo 스택이 비워진다 (테스트)
- 제안 대기 중 사용자 PATCH는 409를 받는다 (테스트)
- `read_document()`가 **사용자가 직접 수정한 최신 내용**을 반환한다 (사용자 PATCH 후 읽기 테스트)
- `propose_insert_lines` / `propose_delete_lines` 적용 후 `order`가 0부터 빈틈없이 매겨진다
- 잘못된 `line_id`로 tool call이 오면 오류를 LLM에 되돌려주고 서버가 죽지 않는다
- 한 턴의 도구 호출이 상한을 넘으면 루프가 강제 종료되고, 그때까지의 제안이 제출된다 (테스트)
- LLM 턴이 예외로 끝나도 잠금이 해제된다 (테스트)
- 잠금이 타임아웃을 넘기면 자동 해제된다 (테스트)
- `GET /documents/{id}/export.md`가 줄을 order 순으로 이은 마크다운을 반환한다 (테스트)
- **문서 코어는 대화 코어를 import하지 않고, 그 반대도 아니다** (구조 테스트 또는 린트로 검증)
- LLM 모듈이 문서 코어를 직접 import하지 않는다 (구조 테스트)
- `POST /documents/{id}/format`이 문서를 직접 바꾸지 않고 제안을 만든다 (테스트)
- 일괄 서식 진행 중 문서가 잠기고, 제안 처리 후 해제된다 (테스트)
- (`mode=apply`의 서식 품질은 LLM 재량 — 기계검증 대상이 아니다. 사람이 diff로 판단)

### M4 — 통합
- 실제 gpt-oss 엔드포인트로 유스케이스 4·6·7이 수동 재현된다
- 프론트에서 로그인 → 세션 생성 → 대화 → 캔버스 갱신 → 직접 편집 → 재요청이 끊김 없이 동작한다
- LLM 편집안 생성 중 캔버스가 블러 처리되고 입력이 막히며, 제안 처리 후 정상 복귀한다
- diff가 추가/삭제로 구분되어 보이고, 적용·취소가 의도대로 동작한다

## 10. 리스크·미결

### 결정이 필요한 것
- **[블로커] LLM의 tool calling 지원 여부** — 캔버스 전체가 여기 얹혀 있다. 지원이 불완전하면 대안(구조화 출력 파싱)으로 선회해야 하므로 **M0에서 제일 먼저 실측**한다.
  모델(gpt-oss-120b)은 사양을 보고 나중에 바꿀 수 있다. 그래서 `llm/base.py` 인터페이스 뒤에 가둔다 — 교체가 `llm/` 안에서 끝나야 한다.
- **[열림] 클라이언트 쪽 잠금 해제 보호** — SSE 재연결 중 해제 통지를 놓치면 블러가 안 걷힌다. 프론트 타임아웃·폴링·재동기화 중 무엇으로 할지.
- **[열림] 여러 줄에 걸친 마크다운 구조** — 코드 펜스, 표, 여러 줄 인용은 줄 여러 개로 나뉜다. LLM이 그중 한 줄만 고치면 구조가 깨질 수 있다. 도구 설명으로 유도할지, 검증으로 막을지.
- **[열림] absorb용 LLM** — 본 응답과 같은 모델을 쓸지, 더 작은 모델을 쓸지. 같은 걸 쓰면 매 absorb마다 120B를 한 번 더 태운다.
- **[열림] 비로그인 임시 세션** — 로그인 없이 써볼 수 있게 할지, 로그인 필수로 갈지.
- **[열림] Redis 유실 시 동작** — Postgres에서 복원하면 마지막 플러시 시점으로 돌아간다. 사용자에게 알릴지, 조용히 넘어갈지.
- **[열림] 파일 업로드·RAG** — 현재 Out of scope. (이미지는 제외 확정)
- **[열림] 디자인 언어** — Figma 시안이 언제 나오나. UI 태스크가 여기 묶인다.
- **[열림] 해커톤 일정·제출 마감** — 미확인. 범위를 더 쳐낼지 판단하려면 필요.

### 실측 후 정할 값
- 버퍼 크기 N과 absorb 주기
- undo 스택 깊이 · 제안 TTL
- 플러시 debounce 간격 — 짧으면 DB 부하, 길면 유실 구간이 커진다
- 편집 잠금 TTL — 긴 응답을 감당하면서 사고 시 오래 잠기지 않을 값

### 확정된 것 (결정 기록)
| 항목 | 결정 |
|---|---|
| 블록 경계 | **줄 단위.** 빈 줄도 블록 |
| 블록 content 포맷 | 마크다운 |
| 문서 개수 | 세션당 정확히 하나 |
| LLM 쓰기 권한 | 없음. 제안 → diff → 사용자 승인 |
| 편집 이력 | Redis 스냅샷 스택. LLM 편집 적용 직전 스냅샷 필수 |
| 실행취소 범위 | 서버 보관. 새로고침해도 유지 |
| 동시 접속 | 계정당 한 환경. 열려 있는 세션은 읽기 전용 잠금 |
| 동시 편집 충돌 | 세마포어 잠금 (LLM 작업 중·제안 대기 중 차단 + 블러) |
| 세션 컨테이너 | 비상주. 요청마다 Redis 복원. 버퍼 + absorb 요약 |
| 세션 제목 | absorb가 자동 생성. 사용자가 정하면 덮어쓰지 않음 |
| 붙여넣기 분할 | 개행으로 자름 (줄 단위이므로 자명) |
| 일괄 서식 판정 | LLM에 일임. 기계검증 대상 아님 |
