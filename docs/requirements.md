# 민원 작성 도우미 — 요구사항 · 개발 계획

_2026-08-27 · 상태: 검토 중_

이 문서는 **무엇을 왜 만드는지의 단일 진실원천(SSoT)** 이다.
구현 중 스펙이 바뀌면 이 문서를 고친다. 결정의 배경과 과정은 `dev-log.md`에 쌓는다.

**처음 읽는다면** 1장 → 3장 → 5장 → 4장 순으로 보면 전체 그림이 잡힌다.

---

## 1. 무엇을 만드나

**시설 민원을 대화로 작성해 문서로 완성하는 웹 도구.**

사용자가 겪은 일을 채팅으로 설명하면, LLM이 그것을 민원 문서로 정리해 **제안**한다.
사용자는 옆 화면(캔버스)에서 그 제안을 보고 적용하거나 거절하고, 직접 고칠 수도 있다.

핵심 성질 하나로 요약하면 이렇다.

> **LLM은 문서를 소유하지 않는다.** 필요할 때 함수로 읽고, 고치고 싶으면 제안만 한다.
> 문서를 실제로 바꾸는 것은 언제나 사용자다.

이 성질에서 두 가지가 따라온다.
- 사용자가 문서를 아무리 자유롭게 고쳐도 LLM이 들고 있는 정보가 낡지 않는다. 매번 새로 읽기 때문이다.
- LLM이 사용자의 작업을 통째로 날려버리는 사고가 구조적으로 불가능하다.

---

## 2. 누가 쓰나

**민원을 넣고 싶은데 어떻게 써야 할지 모르는 사람.**
"복도 등이 두 달째 안 들어온다" 정도만 말할 수 있으면 되고, 문서 형식은 도구가 맡는다.

- 로그인한 사용자는 자기 세션과 자기 문서만 본다.
- 공유·협업은 없다. 한 문서에는 주인이 한 명이다.
- 만드는 쪽은 해커톤 팀이고, 심사용 데모가 결과물이다.

## 3. 범위

### 이번에 만드는 것

| 영역 | 내용 |
|---|---|
| **계정** | 가입 · 로그인 · 로그아웃 · 비밀번호 변경 · 회원 탈퇴 |
| **세션** | 새 대화 시작, 과거 대화 목록, 이어서 대화, 이름 변경·삭제, 제목 자동 생성 |
| **대화** | 텍스트 주고받기, 응답 토큰 스트리밍 |
| **캔버스** | 마크다운 문서 하나(세션당 1개). 사용자가 자유롭게 편집 |
| **제안·승인** | LLM의 편집을 diff로 보여주고 사용자가 적용/취소 |
| **되돌리기** | 실행취소 · 다시실행. 서버에 보관해 새로고침해도 유지 |
| **문서 작업** | `.md` 다운로드, 복사·잘라내기·붙여넣기 |
| **일괄 서식** | 버튼 하나로 문서 전체의 마크다운 서식을 걷어내거나 정리 |
| **동시 접속 차단** | 한 계정은 한 곳에서만. 열려 있는 세션은 다른 곳에서 읽기 전용 |

### 이번에 안 하는 것

- **협업·공유** — 공유 링크, 공동 편집, 권한 관리
- **LLM이 이미지를 만들거나 추천하는 것**
- **PDF·문서 파일 첨부**
- **AWS 프로비저닝·배포** — Kiro IDE에서 별도로 처리한다. 이 저장소는 애플리케이션 코드와 git까지
- **공들인 UI** — 화면은 대화와 캔버스 두 칸이면 충분하다

### 다음에 붙일 것 → 11장

민원서 양식과 사진 첨부는 2차로 미뤘다. 1차 구조가 그것을 그대로 받아내도록 설계돼 있다.

## 4. 사용자가 하는 일

1. **가입하고 로그인한다.** 이후 요청은 로그인 상태로 인증된다.
2. **새 대화를 연다.** 몇 마디 오가면 세션에 제목이 자동으로 붙는다.
3. **과거 대화를 이어간다.** 목록에서 고르면 그때의 대화와 그때의 문서가 그대로 돌아온다.
4. **LLM이 문서를 제안한다.** "정리해줘"라고 하면 캔버스에 diff가 뜬다 — 들어갈 줄은 `+`, 빠질 줄은 `−`.
   **적용**을 누르면 그때 문서가 바뀌고, **취소**를 누르면 문서는 그대로다.
5. **직접 고친다.** 캔버스에서 문장을 바꾸고 줄을 넣고 지운다.
6. **고친 걸 반영시킨다.** "이거 더 다듬어줘"라고 하면 LLM이 **지금의 본문**을 읽어서 작업한다.
7. **일부만 고친다.** "세 번째 문단만 짧게" → 그 줄만 바뀌는 제안이 오고, diff에도 그 줄만 나타난다.
8. **되돌린다.** 적용한 게 마음에 안 들면 실행취소로 직전 상태로. 다시실행으로 복구.
9. **서식을 정리한다.** "서식 제거"를 누르면 마크다운 문법이 걷힌 평문이 되고, "서식 적용"을 누르면
   제목·목록·강조가 붙는다. 둘 다 제안으로 뜨고 승인을 거친다.
10. **받아 간다.** `.md` 파일로 내려받는다.

## 5. 아키텍처

백엔드는 **두 개의 코어와 하나의 조율자**로 나뉜다.

```
                  ┌──────────────────────────────┐
                  │        오케스트레이터         │
                  │         (턴 실행기)           │
                  │   · 한 턴의 수명 관리         │
                  │   · 도구 호출 루프 (상한 있음)│
                  │   · 잠금 획득 / 해제          │
                  │   · 저장 트리거               │
                  │   · SSE 이벤트 발행           │
                  └───┬───────────┬───────────┬──┘
                      │           │           │
          ┌───────────▼───┐ ┌─────▼──────┐ ┌──▼───────────┐
          │   대화 코어    │ │  문서 코어  │ │ LLM 클라이언트 │
          ├───────────────┤ ├────────────┤ ├──────────────┤
          │ 메시지 버퍼    │ │ 줄 목록     │ │ 스트리밍      │
          │ 맥락 요약      │ │ 제안 버퍼   │ │ 도구 호출     │
          │ 제목 자동생성  │ │ 되돌리기 스택│ │              │
          │ Redis 작업본   │ │ 편집 잠금   │ │              │
          └───────────────┘ │ Redis 작업본│ └──────────────┘
                  ▲         └────────────┘
                  │                ▲
                  └── 서로 모른다 ──┘
```

### 두 코어

**대화 코어**는 대화만 안다. 메시지 버퍼, 맥락 요약, 세션 제목을 관리한다.
문서 내용을 상태로 들고 있지 않다.

**문서 코어**는 문서만 안다. 줄을 다루고, 제안을 쌓고, 잠금과 되돌리기를 관리한다.
대화가 있는지도 모른다.

둘은 **서로를 import하지 않는다.** 이 규칙을 테스트로 강제한다.

### 조율자가 따로 있는 이유

두 코어에 걸치는 일이 있다.

- 사용자가 제안을 승인하면 → 문서를 바꾸고, 그 결과를 대화에 기록해야 한다
- 일괄 서식 버튼은 → 채팅 메시지가 아닌데 LLM 턴을 돌린다
- 잠금은 → 턴의 수명과 함께 산다

이걸 어느 코어에 넣어도 "서로 모른다"가 깨진다. 그래서 **걸치는 일은 전부 오케스트레이터가 갖는다.**
오케스트레이터는 상태를 소유하지 않는다. 순서와 수명만 관리한다.

## 6. 데이터와 계약

### 6.1 문서는 줄의 목록이다

문서는 마크다운이고, **한 줄이 곧 하나의 블록**이다. 빈 줄도 블록이다(문단을 가르므로).
문서 전체 = 줄을 순서대로 개행으로 이은 마크다운.

**왜 줄 단위인가.** diff의 단위와 편집의 단위가 같아진다. `+`/`−` 표시가 곧 블록 하나의
추가·삭제이므로 diff 계산·표시·되돌리기가 전부 같은 좌표계 위에서 돈다.

**왜 id로 가리키나.** 줄 번호나 문자 위치로 가리키면, 사용자가 위쪽에 한 줄만 넣어도 전부 밀린다.
안정적인 id라야 사용자의 자유 편집과 LLM의 수정이 같은 문서 위에서 공존한다.

### 6.2 PostgreSQL — 확정된 것만

```
user ──< session ──< message
              └──── document ──< line
```

| 테이블 | 컬럼 |
|---|---|
| `user` | id, email, password_hash, created_at |
| `session` | id, user_id, title, is_manual_title, created_at, updated_at |
| `message` | id, session_id, role(`user`/`assistant`/`system`), content, created_at |
| `document` | id, session_id — **세션당 정확히 하나.** 세션을 만들 때 함께 생긴다 |
| `line` | id, document_id, order, content, updated_at |

- 제안의 적용·거절 결과는 `system` 역할 메시지로 남긴다. 다음 턴에 LLM이 그걸 읽는다.
- `order`는 플러시할 때 0부터 다시 매긴다. 줄을 넣을 때마다 뒤를 미는 연산은 하지 않는다.
- **잠금·제안·되돌리기 스택은 Postgres에 두지 않는다.** 전부 휘발성이므로 Redis가 유일한 진실원천이다.

### 6.3 Redis — 작업본과 휘발 상태

**대화 코어**
- `session:{id}:meta` — 제목, 맥락 요약, 수동 제목 여부
- `session:{id}:buf` — 최근 메시지 버퍼
- `session:{id}:count` — 사용자 메시지 누적 수

**문서 코어**
- `doc:{id}:lines` — 줄 목록 **작업 사본.** 편집은 전부 여기서 일어난다
- `doc:{id}:dirty` — 마지막 저장 이후 변경 여부
- `doc:{id}:proposal` — 승인 대기 중인 제안 (TTL)
- `doc:{id}:undo` / `doc:{id}:redo` — 스냅샷 스택
- `doc:{id}:lock` — 편집 잠금 (TTL로 자동 해제)

**접속 제어**
- `user:{id}:active` — 계정의 현재 활성 접속
- `session:{id}:held_by` — 이 세션을 열고 있는 접속 (heartbeat로 TTL 갱신)

**그 외**: 로그인 세션, 스트리밍 재연결 버퍼

### 6.4 LLM에게 주는 함수

**읽기 — 즉시 실행된다**
- `read_document()` → `[{id, order, content}]`

**쓰기 — 제안으로만 쌓인다. 문서는 바뀌지 않는다**
- `propose_replace_line(line_id, text)`
- `propose_insert_lines(after_line_id | null, texts[])` — null이면 맨 앞
- `propose_delete_lines(line_ids[])`
- `propose_replace_document(lines[])` — 전체 재작성 (초안 생성, 일괄 서식)

**한 턴 안에서 `read_document()`가 보는 것**: 이미 쌓인 제안을 **반영한 결과**를 돌려준다.
그래야 LLM이 연속으로 편집할 수 있다 — 방금 자기가 고친 줄을 원래 상태로 다시 보면
같은 수정을 반복하거나 이미 지운 줄을 또 지우려 든다.
LLM 시점에서는 "쓴 대로 보인다". 다만 그것은 제안 위에 얹힌 **가상의 뷰**이고,
실제 작업본은 승인 전까지 손대지 않는다.

### 6.5 HTTP API

**계정**
```
POST   /auth/signup
POST   /auth/login
POST   /auth/logout
GET    /auth/me
PATCH  /auth/password          현재 비밀번호 확인 후 변경
DELETE /auth/me                탈퇴 — 세션·문서·줄 일괄 삭제
```

**세션**
```
GET    /sessions               목록 (커서 페이지네이션)
POST   /sessions               생성 — 빈 문서가 함께 만들어진다
GET    /sessions/{sid}
PATCH  /sessions/{sid}         제목 변경 (이후 자동 갱신 안 함)
DELETE /sessions/{sid}
POST   /sessions/{sid}/open        점유 등록
POST   /sessions/{sid}/heartbeat   점유 갱신
```

**대화**
```
GET    /sessions/{sid}/messages    대화 이력 (커서 페이지네이션)
POST   /sessions/{sid}/messages    메시지 전송 — 제안이 떠 있으면 409
GET    /sessions/{sid}/stream      SSE
```

**문서** — 세션당 하나이므로 문서 id를 URL에 노출하지 않는다.
소유자 확인이 `{sid}` 한 곳에서 끝나고, 문서 id를 찾는 단계가 사라진다.
```
GET    /sessions/{sid}/document                줄 목록 + 잠금 상태 + 제안 유무
PATCH  /sessions/{sid}/document/lines/{lid}    한 줄 수정
POST   /sessions/{sid}/document/lines          줄 삽입
DELETE /sessions/{sid}/document/lines          줄 삭제
GET    /sessions/{sid}/document/export.md      다운로드
POST   /sessions/{sid}/document/format         {mode: "strip" | "apply"} → 제안으로 뜬다
GET    /sessions/{sid}/document/proposal       현재 제안과 diff
POST   /sessions/{sid}/document/proposal/accept
POST   /sessions/{sid}/document/proposal/reject   body에 선택적 reason
POST   /sessions/{sid}/document/undo
POST   /sessions/{sid}/document/redo
```

**응답 코드**

| 코드 | 의미 |
|---|---|
| 401 | 로그인하지 않음 |
| 403 | 로그인했으나 소유자가 아님 |
| 404 | 없거나 볼 권한이 없음 (존재 여부를 흘리지 않는다) |
| 409 | 잠금 충돌 — 문서 편집 잠금 중, 제안이 떠 있는데 새 턴 시도, 세션이 다른 곳에서 열림 |
| 422 | 요청 형식 오류 (없는 `line_id` 등) |

### 6.6 SSE 이벤트

채널은 **세션당 하나**다. 대화와 문서 이벤트가 같은 채널로 온다 —
둘은 한 턴 안에서 엮여 일어나므로 채널을 나누면 순서 보장이 깨진다.

| 이벤트 | 언제 | 내용 |
|---|---|---|
| `token` | 응답 토큰 도착 | 텍스트 조각 |
| `tool_start` / `tool_end` | 도구 호출 시작·종료 | 도구 이름 |
| `lock` / `unlock` | 잠금 상태 변경 | 사유 (`llm_editing` / `proposal_pending` / `held_elsewhere`) |
| `proposal` | 제안 준비 완료 | 제안 id, diff |
| `proposal_resolved` | 적용·거절·만료 처리됨 | 결과, 갱신된 문서 |
| `document_changed` | 사용자 편집·되돌리기로 문서가 바뀜 | 갱신된 문서, `origin` |
| `session_meta` | 제목·요약 갱신 | 새 제목 |
| `turn_end` | 턴 종료 | — |
| `error` | 턴 실패 | 사유 |

**메아리 방지**: 문서를 바꾸는 요청에 클라이언트가 식별자를 실어 보내면 서버가 그걸
`document_changed`의 `origin`으로 되돌려준다. 프론트는 자기 `origin`이면 무시한다.
그러지 않으면 자기가 친 글자가 이벤트로 되돌아와 커서가 튄다.

**잠금은 서버가 진실원천이다.** 프론트는 `lock`/`unlock` 신호를 유일한 근거로 삼지 않는다.
재연결 중에 신호를 놓칠 수 있으므로, 잠금 상태일 때는 주기적으로 서버에 다시 물어 확인한다.

## 7. 동작 규약

### 7.1 한 턴의 흐름

```
사용자 메시지 도착
  │  ※ 떠 있는 제안이 있으면 여기서 409로 거절
  ├─ 사용자 메시지를 먼저 저장한다 (이후 실패해도 남는다)
  ├─ 대화 코어에서 맥락 조립 (버퍼 + 요약 + 직전 제안 처리 결과)
  ├─ LLM 스트리밍 시작 ─────────────────► token
  ├─ 도구 호출이 오면
  │     read_document   문서 코어에 질의 → 결과 반환 (즉시)
  │     propose_*       제안 버퍼에 적재
  │                     첫 propose에서 문서 잠금 ──► lock
  │     ※ 도구 호출 루프에는 턴당 상한이 있다.
  │        넘으면 강제 종료하고 그때까지의 제안을 제출한다.
  ├─ 응답 종료
  ├─ 제안이 있으면 diff 계산 ───────────► proposal
  │  제안이 없으면 잠금 해제 ───────────► unlock
  ├─ 대화 코어에 턴 커밋
  ├─ 저장 트리거
  └─ (뒤에서) 필요하면 요약 실행 ────────► session_meta
```

**턴이 실패하면**: 사용자 메시지는 이미 저장돼 있으므로 남는다. 부분 응답은 버린다.
잠금이 걸려 있었으면 반드시 푼다. `error` 이벤트를 보낸다. 문서는 손대지 않는다.

### 7.2 제안 · 승인

1. LLM이 쓰기 함수를 호출하면 **제안 버퍼**에 쌓인다. 작업본은 그대로다.
2. 턴이 끝나면 문서 코어가 **현재 문서 ↔ 제안 적용 결과**를 비교해 diff를 만든다.
3. 캔버스에 diff가 뜬다. 들어갈 줄 `+`, 빠질 줄 `−`.
4. 사용자가 고른다.
   - **적용** — 직전 상태를 되돌리기 스택에 넣고 → 작업본에 반영 → 다시실행 스택 비움 → 저장
   - **취소** — 제안을 버린다. 문서는 손대지 않는다.
5. 제안이 떠 있는 동안 **문서를 바꾸는 모든 경로가 잠긴다.**

   | 잠기는 것 | 왜 |
   |---|---|
   | 사용자 직접 편집 | 그 사이 고치면 제안의 기준 문서가 어긋난다 |
   | 채팅 새 메시지 | 제안을 겹쳐 쌓지 않기 위해 |
   | 일괄 서식 버튼 | 같은 이유 — 또 하나의 LLM 턴이므로 |
   | 실행취소·다시실행 | 기준이 바뀌면 diff가 무의미해진다 |

   **되는 것**: 읽기, 복사, 다운로드, 그리고 적용·취소.

6. **살아 있는 제안은 항상 최대 하나.** 이 불변식 하나로 제안 큐·순서·충돌 처리가 통째로 사라진다.
7. 제안에는 TTL이 있다. 방치되면 만료된다. **만료는 거절과 같다** — 문서를 손대지 않고 잠금도 함께 푼다.
   `proposal_resolved`로 알린다. 화면이 조용히 잠긴 채 남지 않게.
8. **처리 결과를 LLM이 안다.** 적용됐는지 거절됐는지가 대화에 기록되어 다음 턴에 실린다.
   거절된 걸 또 내밀거나 이미 적용된 걸 다시 제안하지 않게. 사용자가 거절 사유를 짧게 남기면 그것도 전달된다.

### 7.3 되돌리기

- Redis 스냅샷 스택. 줄 목록 전체를 통째로 담는다. 문서가 줄 목록이라 스냅샷이 가볍다. 깊이 상한을 둔다.
- **LLM 편집을 적용하기 직전에 반드시 스냅샷을 남긴다.** 승인한 게 마음에 안 들어도 한 번에 돌아간다.
- 단위는 **확정된 편집 하나**. LLM 제안 적용분과 사용자 편집이 같은 스택을 쓴다.
- 새 편집이 확정되면 다시실행 스택을 비운다.
- 서버에 두므로 새로고침해도 살아 있다.

### 7.4 저장 — Redis 작업본에서 Postgres로

두 코어가 같은 방식으로 돈다.

1. 요청이 오면 Redis에서 상태를 복원한다. 없으면 Postgres에서 읽어 Redis에 올린다.
2. 편집은 **Redis 작업본에만** 반영한다. 글자 하나 칠 때마다 DB를 때리지 않는다.
3. 트리거가 걸리면 Postgres에 **통째로 덧씌운다.**

   트리거: 턴 종료 · 제안 승인 · 실행취소·다시실행 · 사용자 편집 후 일정 시간 무입력 ·
   다운로드 · 일괄 서식 실행 · 세션 이탈(heartbeat 끊김)

4. 저장은 **전체 덮어쓰기**다. 부분 병합을 하지 않는다 — 작업본이 곧 정답이므로.
5. **저장이 실패하면 dirty 표시를 지우지 않는다.** 작업본은 Redis에 그대로 있고 다음 트리거에서 다시 시도한다.
   사용자 요청을 실패로 만들지 않는다. 편집은 이미 작업본에 들어가 있기 때문이다.

**감수하는 것**: 마지막 저장 이후 Redis가 죽으면 그 구간의 편집은 사라진다.
이걸 받아들이는 대신 편집 반응성을 얻는다. 손실 구간의 크기는 무입력 대기 시간이 정한다.

### 7.5 대화 상태 관리

1. **상주하지 않는다.** 요청마다 상태를 Redis에서 복원한다.
2. **버퍼 + 요약**: 최근 메시지 몇 개만 버퍼에 두고, 그보다 오래된 맥락은 요약 문자열 하나로 압축해 들고 간다.
3. **요약(absorb)**: 버퍼가 차거나 첫 메시지일 때, 별도 LLM 호출로 대화를 압축해 **제목**과 **요약**을 새로 뽑고
   버퍼를 비운다. 세션 제목이 여기서 자동으로 갱신된다.
   - **뒤에서 돈다.** 턴 응답을 먼저 끝내고 실행한다. 사용자를 기다리게 하지 않는다.
   - 끝나면 `session_meta`로 새 제목을 밀어준다.
   - **실패해도 대화는 멀쩡해야 한다.** 기존 제목·요약을 유지하고 버퍼도 비우지 않는다. 다음 기회에 다시 시도한다.
   - 요약이 도는 중에 다음 턴이 시작될 수 있다. 버퍼 갱신이 엉키지 않도록 세션 단위로 직렬화한다.
4. 사용자가 제목을 직접 정하면 그 뒤로 자동 갱신이 덮어쓰지 않는다.

> **화면에 보이는 대화와 LLM이 읽는 맥락은 다르다.**
> 화면에는 Postgres의 **전체 메시지**를 보여준다 — 사용자는 처음부터 다 볼 수 있어야 한다.
> LLM에는 **버퍼 + 요약**만 넣는다 — 맥락 길이를 일정하게 유지하기 위해서다.
> 이 둘을 같은 것으로 만들면 안 된다.

### 7.6 동시 접속 차단

같은 문서를 두 화면이 각자 편집하면 Redis 작업본이 엉킨다. 두 겹으로 막는다.

1. **계정 단위** — 한 계정은 한 곳에서만 접속한다. 다른 곳에서 로그인하면 기존 접속이 밀려난다.
2. **세션 단위** — 이미 열려 있는 세션에 접근하면 블러 처리하고 "다른 곳에서 작업 중"으로 표시한다.
   읽기만 되고 편집은 막힌다.
   - 점유는 **로그인 세션에 묶는다.** 같은 로그인 세션이 다시 열면(새로고침) TTL을 기다리지 않고 즉시 되찾는다.
     그러지 않으면 새로고침 한 번에 자기 세션이 수십 초 잠긴다.
   - 다른 로그인 세션이면 TTL이 끝날 때까지 읽기 전용.

**왜 두 겹인가.** 1번만으로는 부족하다. 밀려난 화면이 그 사실을 알기까지 시차가 있고,
탭 복제로 같은 자격증명이 잠시 둘일 수 있다. 1번은 정책이고, 2번은 문서에 실제로 손대는 시점의 자물쇠다.

잠금 화면은 LLM 편집 잠금과 같은 것을 쓴다. 블러 + 입력 차단, 문구만 다르다.

## 8. 기술 스택과 제약

### 스택

| 층 | 선택 |
|---|---|
| 프론트엔드 | React + Vite + TypeScript (시안은 Figma) |
| 백엔드 | Python + FastAPI |
| LLM | 로컬 gpt-oss-120b, OpenAI 호환 엔드포인트로 서빙. **도구 호출 사용** |
| 영속 저장 | PostgreSQL |
| 휘발 저장 | Redis |
| 컨테이너 | Docker (이 저장소의 `docker/`는 로컬 개발용) |
| 배포 | AWS — Kiro IDE 담당, 이 저장소 범위 밖 |

### 제약

- **도구 호출이 전제다.** 캔버스 전체가 그 위에 서 있다. 착수 전 실측으로 확인한다.
  모델은 사양을 보고 바꿀 수 있다. 그래서 LLM 클라이언트 인터페이스 뒤에 가둔다 — 교체가 그 안에서 끝나야 한다.
- **인증은 HttpOnly 쿠키 세션.** 세션 id를 쿠키에 싣고 실체는 Redis에 둔다.
  - `EventSource`는 커스텀 헤더를 붙이지 못한다. 쿠키는 자동으로 실리므로 SSE가 그대로 인증된다.
  - 토큰이 JS에 노출되지 않는다.
  - 서버가 세션을 지울 수 있어 강제 로그아웃과 단일 접속 강제가 즉시 먹는다.
  - `SameSite=Lax` + 상태를 바꾸는 요청에는 커스텀 헤더를 요구해 교차 사이트 요청을 막는다.
- **SSE는 장수명 연결이다.** 연결할 때만 인증을 보지 않는다.
  로그인 세션이 사라지면(만료·강제 로그아웃·다른 곳 로그인) 서버가 스트림을 끊는다.
- **인가** — 모든 세션·문서 접근은 소유자 확인을 거친다. 남의 id를 넣어도 보이지 않는다.
- **비밀번호는 해시로만 저장한다.** 평문 금지.
- **시크릿은 `.env`에만.** 코드는 환경변수를 읽기만 하고 실제 값은 사람이 채운다.
- **모든 반복에 상한이 있다** — 턴당 도구 호출 횟수, 되돌리기 스택 깊이, 요약 재시도.
  상한 없는 반복을 두지 않는다.
- **잠금은 반드시 풀린다.** 응답 실패·연결 끊김에도 영구히 잠기지 않도록 TTL로 자동 해제한다.
- 해커톤 기간 안에 만들 수 있을 것. 애매하면 기능을 쳐낸다.

## 9. 마일스톤과 완료 기준

각 항목은 테스트나 명령으로 판정한다. "동작한다"는 통과 기준이지 "보기 좋다"는 아니다.

### M0 — 스켈레톤과 실측

- [ ] **LLM 엔드포인트에 도구를 붙여 호출하면 도구 호출이 규격대로 돌아온다** (probe 스크립트로 실측)
      — **이것이 첫 태스크다.** 실패하면 구조화 출력 파싱으로 방향을 틀어야 하므로 뒤 작업을 시작하지 않는다.
- [ ] `docker compose -f docker/compose.dev.yml up`으로 postgres·redis·backend·frontend가 뜬다
- [ ] `GET /health`가 200과 함께 postgres·redis·LLM 엔드포인트 도달 여부를 반환한다
- [ ] `pytest`가 실패 0으로 통과한다

### M1 — 계정

- [ ] 가입 → 로그인 → `GET /auth/me`가 그 사용자를 돌려준다
- [ ] 틀린 비밀번호로 로그인하면 401
- [ ] DB에 평문 비밀번호가 없다
- [ ] 로그인 없이 `/sessions`를 부르면 401
- [ ] 세션 쿠키가 HttpOnly로 내려간다
- [ ] 같은 계정으로 두 번째 로그인하면 첫 번째 접속이 무효화되고, 기존 쿠키로 부르면 401
- [ ] 비밀번호 변경 후 옛 비밀번호로 로그인하면 401
- [ ] 탈퇴하면 그 계정의 세션·문서·줄이 전부 사라진다

### M2 — 세션과 대화

- [ ] 세션을 만들면 목록에 나타나고, 빈 문서가 함께 생긴다
- [ ] 다른 사용자의 세션은 목록에 없고, 그 id로 접근하면 404
- [ ] 메시지를 보내면 저장되고 SSE로 토큰이 스트리밍된다 (가짜 LLM으로 결정론적 검증)
- [ ] **과거 세션을 열면 전체 대화 이력과 그때의 문서가 복원된다**
- [ ] 턴이 실패해도 사용자 메시지는 저장돼 있고, 잠금이 풀리고, `error` 이벤트가 온다
- [ ] 요약이 실패해도 턴 응답은 정상이고 기존 제목·요약이 유지된다
- [ ] 세션을 지우면 Postgres의 메시지·문서·줄과 **Redis 잔재(작업본·제안·이력·잠금·점유)가 함께** 사라진다
- [ ] 이미 열려 있는 세션에 **다른 로그인 세션**이 들어오면 읽기 전용으로 응답한다
- [ ] **같은 로그인 세션**이 다시 열면 TTL을 기다리지 않고 즉시 편집할 수 있다

### M3 — 문서 코어

- [ ] 가짜 LLM이 쓰기 함수를 불러도 **문서가 즉시 바뀌지 않는다.** 제안만 생긴다
- [ ] 제안을 적용해야 그 줄이 바뀌고, 다른 줄은 그대로다
- [ ] 제안을 거절하면 문서가 호출 전과 완전히 같다
- [ ] 처리 결과가 다음 턴 LLM 맥락에 들어간다
- [ ] 한 턴 안에서 `propose` 후 `read_document()`를 부르면 **제안이 반영된 뷰**가 나온다
- [ ] 그 시점에 실제 작업본은 아직 바뀌지 않았다
- [ ] `read_document()`가 **사용자가 방금 고친 내용**을 돌려준다
- [ ] 실행취소하면 직전 상태와 일치하고, 다시실행으로 복귀한다
- [ ] 새 편집이 확정되면 다시실행 스택이 비워진다
- [ ] 제안 대기 중 `PATCH lines` · `POST messages` · `format` · `undo` · `redo`가 모두 409
- [ ] 제안 대기 중에도 `GET document` · `export.md` · `accept` · `reject`는 정상
- [ ] 제안이 TTL로 만료되면 문서가 그대로이고 잠금이 풀린다
- [ ] 줄 삽입·삭제 후 `order`가 0부터 빈틈없이 매겨진다
- [ ] 없는 `line_id`로 도구가 불리면 오류를 LLM에 돌려주고 서버가 죽지 않는다
- [ ] 도구 호출이 턴 상한을 넘으면 루프가 강제 종료되고 그때까지의 제안이 제출된다
- [ ] 턴이 예외로 끝나도, 잠금이 TTL을 넘겨도 잠금이 해제된다
- [ ] `export.md`가 줄을 순서대로 이은 마크다운을 돌려준다
- [ ] `format`이 문서를 직접 바꾸지 않고 제안을 만든다
- [ ] **문서 코어와 대화 코어가 서로를 import하지 않는다** (구조 테스트)
- [ ] **LLM 모듈이 문서 코어를 직접 import하지 않는다** (구조 테스트)

### M4 — 통합

- [ ] 실제 LLM 엔드포인트로 사용자 흐름 4·6·7이 재현된다
- [ ] 로그인 → 세션 생성 → 대화 → 캔버스 갱신 → 직접 편집 → 재요청이 끊김 없이 동작한다
- [ ] LLM 작업 중 캔버스가 블러 처리되고 입력이 막히며, 제안 처리 후 정상 복귀한다
- [ ] diff가 추가·삭제로 구분되어 보이고 적용·취소가 의도대로 동작한다

## 10. 정해야 할 것

### 착수 전에 확인

- **LLM의 도구 호출 지원** — 캔버스 전체가 여기 얹혀 있다. M0 첫 태스크로 실측한다.
  안 되면 구조화 출력 파싱으로 방향을 튼다.

### 만들면서 정할 것

- **여러 줄에 걸친 마크다운** — 코드 펜스, 표, 여러 줄 인용은 줄 여러 개로 나뉜다.
  LLM이 그중 한 줄만 고치면 구조가 깨질 수 있다. 도구 설명으로 유도할지, 검증으로 막을지.
- **요약용 모델** — 본 응답과 같은 모델을 쓸지, 더 작은 걸 쓸지. 같은 걸 쓰면 요약할 때마다 120B를 한 번 더 태운다.
- **잠금 해제 신호를 놓쳤을 때** — 재확인 주기를 얼마로 할지.
- **Redis가 죽었을 때** — Postgres에서 복원하면 마지막 저장 시점으로 돌아간다. 사용자에게 알릴지 조용히 넘어갈지.
- **비로그인 체험** — 로그인 없이 써볼 수 있게 할지, 로그인 필수로 갈지.
- **호출 빈도 제한** — LLM 호출은 비싸다. 해커톤 범위에서 둘지.

### 실측 후 정할 값

- 버퍼 크기와 요약 주기
- 되돌리기 스택 깊이, 제안 TTL
- 저장 대기 시간 — 짧으면 DB 부하, 길면 손실 구간이 커진다
- 편집 잠금 TTL — 긴 응답을 감당하면서 사고 시 오래 잠기지 않을 값

### 팀에 확인이 필요한 것

- **해커톤 일정과 제출 마감** — 범위를 더 쳐낼지 판단하는 근거
- **Figma 시안 시점** — UI 작업이 여기 묶인다
- **완성한 민원서를 실제로 제출까지 하는가** — 보낸다면 외부 연동이 붙어 범위가 크게 는다

## 11. 다음에 붙일 것

1차에서 빼되 버리지는 않는다. **1차 구조가 이걸 그대로 받아내도록 설계돼 있다.**

### 11.1 민원서 양식

문서를 백지가 아니라 정해진 양식에서 시작하게 한다.
LLM의 일이 "글쓰기"에서 **"칸 채우기"**로 바뀐다.

- 양식은 **섹션 제목 줄 + 내용 줄**의 마크다운이다. **줄 단위 모델이 그대로 적용된다** — 데이터 모델을 바꿀 필요가 없다.
- 필수 항목이 비었는지 검사해 사용자에게 보여주고, LLM이 대화로 되묻는다
  ("발생 일시가 비어 있는데 언제였나요?").
- 붙는 곳: 문서 코어에 양식 정본과 완성도 검사, `GET .../document` 응답에 완성도 필드.
- **먼저 필요한 것**: 실제 민원서 양식을 구해 필수 항목을 확정해야 한다.

### 11.2 사진 첨부

현장 사진을 올려 민원의 근거로 삼는다.

- 채팅에서 올리고 "이거 어디에 넣어"라고 하면 LLM이 적절한 위치에 넣는 **제안**을 낸다.
- 문서에서는 마크다운 이미지 한 줄(`![설명](...)`)이다. **역시 줄 단위 모델 그대로** — 별도 블록 타입이 필요 없다.
- 필요한 것
  - `attachment` 테이블 — session_id, filename, content_type, size, storage_key, **user_note**
  - **저장소 추상화** — 이미지 바이트를 DB에 넣지 않는다. 로컬 볼륨에서 S3로 교체가 그 안에서 끝나게. DB에는 키만.
  - 함수 `list_attachments()` · `propose_insert_image(after, attachment_id, alt)`
    (이미지 삽입을 일반 줄 삽입과 분리하는 이유: 없는 첨부를 참조하지 못하게)
  - API `POST|GET|DELETE /sessions/{sid}/attachments`
- **알아둘 한계**: 텍스트 모델은 이미지를 보지 못한다. 파일명과 사용자가 붙인 설명만으로 위치를 판단하므로
  배치가 어긋날 수 있다. 제안·승인 구조가 그래서 더 중요해진다.
- 보안: 첨부도 소유자만 접근한다. 저장소 URL을 직접 노출하지 않고 API를 거친다.
  업로드는 서버에서 형식·크기를 검증한다. 확장자만 믿지 않는다.
- 정할 것: 다운로드할 때 이미지 처리(zip / 절대 URL / base64), 첨부를 지웠을 때 문서 줄 처리, 개수·용량 상한.

### 11.3 그 밖의 후보

- 완성한 민원서를 실제 접수처로 제출
- 이메일 기반 비밀번호 재설정
- 비로그인 체험 세션
