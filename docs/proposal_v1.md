## 용어 먼저

이 문서에서 **"세션"은 대화 스레드 하나**만 가리킨다. 인증 쪽은 다른 말을 쓴다.

**세션** 대화 스레드(문서 하나가 딸림) · **로그인** 인증 상태 · **접속** 브라우저 하나의 연결 ·
**줄/블록** 같은 것 · **제안** 승인 전의 편집안 · **작업본** Redis에 있는 편집 중인 사본 ·
**턴** 입력 하나에 대한 응답 한 차례

## 한 줄로

**시설 민원을 대화로 작성해 문서로 완성하는 웹 도구.**
사용자가 겪은 일을 채팅으로 말하면 LLM이 민원 문서로 정리해 **제안**하고, 사용자가 확인해 완성한다.

## 이 설계의 핵심

> **LLM은 문서를 소유하지 않는다.**
> 필요할 때 함수로 읽고, 고치고 싶으면 제안만 한다. 문서를 실제로 바꾸는 것은 언제나 사용자다.

여기서 두 가지가 따라온다.

- 사용자가 문서를 자유롭게 고쳐도 **LLM이 든 정보가 낡지 않는다.** 매번 새로 읽기 때문이다.
- LLM이 사용자의 작업을 통째로 날리는 사고가 **구조적으로 불가능하다.**

화면은 좌우 두 칸이다. 왼쪽에서 대화하고, 오른쪽 캔버스에서 문서가 자란다.

## 어떻게 동작하나

### 구조: 두 개의 코어와 하나의 조율자

```
                 ┌─────────────────────────────┐
                 │       오케스트레이터         │
                 │        (턴 실행기)           │
                 │  턴 수명 · 도구 루프 · 잠금   │
                 │  저장 트리거 · SSE 발행       │
                 └──┬──────────┬──────────┬────┘
                    │          │          │
         ┌──────────▼──┐ ┌─────▼─────┐ ┌──▼──────────┐
         │  대화 코어   │ │ 문서 코어  │ │ LLM 클라이언트│
         ├─────────────┤ ├───────────┤ ├─────────────┤
         │ 메시지 버퍼  │ │ 줄 목록    │ │ 스트리밍     │
         │ 맥락 요약    │ │ 제안 버퍼  │ │ 도구 호출    │
         │ 제목 생성    │ │ 되돌리기   │ │             │
         └─────────────┘ │ 편집 잠금  │ └─────────────┘
                ▲        └───────────┘
                │              ▲
                └─ 서로 모른다 ─┘
```

**대화 코어**는 대화만, **문서 코어**는 문서만 안다.
서로를 import하지 않고, 이 규칙을 테스트로 강제한다.

**조율자가 따로 있는 이유**: 두 코어에 걸치는 일이 있다 — 제안을 승인하면 문서를 바꾸고 그 결과를
대화에 기록해야 하고, 일괄 서식 버튼은 채팅이 아닌데 LLM 턴을 돌리고, 잠금은 턴의 수명과 함께 산다.
어느 코어에 넣어도 "서로 모른다"가 깨지므로 **걸치는 일은 전부 조율자가 갖는다.**
조율자는 상태를 소유하지 않고 순서와 수명만 관리한다.

### 문서는 줄의 목록이다

한 줄이 곧 하나의 블록이다. 빈 줄도 블록이다.

- **왜 줄 단위인가** — diff의 단위와 편집의 단위가 같아진다. `+`/`−` 하나가 곧 블록 하나라
  diff 계산·표시·되돌리기가 전부 같은 좌표계에서 돈다.
- **왜 id로 가리키나** — 줄 번호나 문자 위치로 가리키면 사용자가 위에 한 줄만 넣어도 전부 밀린다.
  안정적인 id라야 사용자 편집과 LLM 수정이 같은 문서 위에 공존한다.

### 제안 → diff → 승인

1. LLM이 쓰기 함수를 부르면 **제안 버퍼**에 쌓인다. 문서는 그대로다.
2. 턴이 끝나면 현재 문서와 제안 적용 결과를 비교해 **diff**를 만들어 캔버스에 띄운다.
   **비교는 줄 id가 아니라 줄 내용으로 한다**(텍스트 diff). id로 비교하면 전체 재작성 제안에서
   내용이 그대로인 줄까지 전부 "바뀜"으로 나와 사람이 볼 수 없는 diff가 된다.
3. 사용자가 **적용**하면 그때 반영되고, **취소**하면 문서는 손대지 않는다.
4. 제안이 떠 있는 동안 문서를 바꾸는 **모든 경로가 잠긴다** — 직접 편집, 새 메시지, 일괄 서식, 되돌리기.
   읽기·복사·다운로드와 적용·취소만 된다.
5. 두 개의 불변식으로 제안 큐·순서·충돌 처리가 통째로 사라진다.
   **살아 있는 제안은 항상 최대 하나**이고, **한 세션에서 턴은 한 번에 하나만 돈다.**
   (턴이 도는 중에 메시지를 또 보내면 409. 없으면 턴 두 개가 같은 메시지 버퍼를 고쳐 맥락이 깨진다.)
6. 처리 결과가 대화에 기록되어 **다음 턴에 LLM이 안다.** 거절된 걸 또 내밀지 않게.
7. 제안에는 TTL이 있고 **만료는 거절과 같다** — 문서를 손대지 않고 잠금도 함께 푼다.

**잠금은 LLM이 문서를 처음 읽는 순간 건다.** 제안을 낼 때가 아니다.
읽은 뒤 제안하기까지 사이에 사용자가 고치면 제안의 기준이 어긋나 엉뚱한 줄이 바뀐다.
읽었다는 건 문서에 관여할 뜻이 있다는 것이므로 그때 잠근다.
문서를 읽지 않는 순수한 대화 턴에서는 잠기지 않으니 캔버스가 쓸데없이 흐려지지 않는다.

잠금 중에는 캔버스가 **블러 처리되고 입력이 막힌다.** 잠금은 반드시 풀린다 —
응답 실패나 연결 끊김에도 TTL로 자동 해제한다.

### 한 턴 안에서 LLM이 보는 것

제안이 만든 새 줄에도 **임시 id가 즉시 붙는다.** 그래야 LLM이 같은 턴에서 방금 넣은 줄을
다시 가리켜 고칠 수 있다. 임시 id는 승인될 때 확정되고 거절되면 함께 사라진다.

`read_document()`는 **이미 쌓인 제안을 반영한 결과**를 돌려준다.
그래야 연속 편집이 된다 — 방금 고친 줄을 원래 상태로 다시 보면 같은 수정을 반복하거나
이미 지운 줄을 또 지우려 든다. LLM 시점에선 "쓴 대로 보이고", 그건 제안 위에 얹힌 가상의 뷰다.
실제 문서는 승인 전까지 그대로다.

### 되돌리기

Redis 스냅샷 스택에 줄 목록을 통째로 담는다. 문서가 줄 목록이라 스냅샷이 가볍다.
LLM 편집을 적용하기 **직전에 반드시 스냅샷을 남긴다.**

**사용자 편집은 글자마다 스냅샷을 남기지 않는다** — 그러면 스택이 순식간에 폭발한다.
편집이 시작될 때 하나 잡고, 무입력으로 저장이 일어나는 시점에 그 묶음을 확정한다.
연속으로 친 것은 한 번에 되돌아간다.

### 저장: Redis 작업본 → Postgres

두 코어가 같은 방식으로 돈다. **상주 객체 없이 요청마다 Redis에서 복원한다.**

편집은 Redis 작업본에만 반영한다. 글자 하나 칠 때마다 DB를 때리지 않는다.
트리거가 걸리면 Postgres에 **통째로 덧씌운다** — 턴 종료, 제안 승인, 되돌리기,
편집 후 일정 시간 무입력, 다운로드, 일괄 서식, 세션 이탈.

부분 병합은 하지 않는다. 작업본이 곧 정답이다.
저장이 실패하면 dirty 표시를 지우지 않고 다음 트리거에서 다시 시도한다.
**저장 안 된 작업본에는 만료를 걸지 않는다** — TTL로 조용히 사라지면 그건 사고가 아니라
설계로 데이터를 버리는 것이다. 저장에 성공한 뒤에야 만료 대상이 된다.

**세션 이탈은 heartbeat가 끊긴 것으로 안다.** 브라우저가 닫히면 아무도 알려주지 않으므로
서버에 주기적으로 도는 **정리 작업**이 있어야 한다 — 점유가 만료됐는데 작업본이 저장 안 됐으면 저장하고,
방치된 제안·잠금·턴 표시를 거둔다. 서버가 여러 대여도 하나만 돌게 잠금을 건다.

> **감수하는 것**: 마지막 저장 이후 Redis가 죽으면 그 구간 편집은 사라진다.
> 이걸 받아들이는 대신 편집 반응성을 얻는다.

### 대화 맥락 관리

최근 메시지 몇 개만 버퍼에 두고, 오래된 맥락은 요약 문자열 하나로 압축한다.
버퍼가 차면 별도 LLM 호출로 대화를 압축해 **제목과 요약**을 새로 뽑고 버퍼를 비운다.
세션 제목이 여기서 자동 갱신된다. 사용자가 직접 정하면 그 뒤론 덮어쓰지 않는다.

요약은 **뒤에서 돈다.** 턴 응답을 먼저 끝내고 실행하므로 사용자를 기다리게 하지 않는다.
실패해도 기존 제목·요약을 유지하고 버퍼도 비우지 않는다.
끝나면 Postgres의 제목을 곧바로 갱신한다 — 세션 목록이 그걸 읽으므로 미루면 옛 제목이 남는다.

> **화면에 보이는 대화 ≠ LLM이 읽는 맥락.**
> 화면에는 Postgres의 전체 메시지를 보여주고, LLM에는 버퍼 + 요약만 넣는다.
> 이 둘을 같은 것으로 만들면 안 된다.

### 접속 제어

같은 문서를 두 화면이 각자 편집하면 작업본이 엉킨다. 두 겹으로 막는다.

1. **계정 단위** — 한 계정은 한 곳에서만. 다른 곳에서 로그인하면 기존 로그인이 밀려난다.
2. **세션 단위** — 이미 점유된 세션에 접근하면 블러 + "다른 곳에서 작업 중". 읽기만 된다.
   점유는 로그인에 묶어서, 같은 로그인이 새로고침하면 즉시 되찾는다.

1번이 정상 경로를 막고 2번이 그 틈을 막는다. 1번은 밀어내는 방식이라
**밀려난 화면이 그 사실을 알기까지 시차가 있고**, 그 사이 옛 화면의 요청이 도착할 수 있다.
탭 복제로 같은 쿠키가 잠시 둘일 수도 있다. 1번은 정책, 2번은 손대는 순간의 자물쇠다.

## 데이터와 계약

### 테이블

```
app_user ──< session ──< message
                  └──── document ──< line
```

`document`는 **세션당 정확히 하나**, 세션을 만들 때 함께 생긴다.
`line`은 마크다운 한 줄. `line_order`는 저장할 때 0부터 다시 매긴다.

> `user`와 `order`는 PostgreSQL 예약어라 `app_user` · `line_order`로 쓴다.
> Redis 키도 문서 id가 아니라 **세션 id로 잡는다**(`doc:{sid}:lines`) — 문서가 세션당 하나이므로
> 문서 id를 찾는 단계가 실제로 사라진다.

**잠금·제안·되돌리기 스택은 Postgres에 두지 않는다.** 전부 휘발성이라 Redis가 유일한 진실원천이고,
Postgres에는 확정된 본문만 남는다.

### LLM에게 주는 함수

| 함수 | 성격 |
|---|---|
| `read_document()` | 읽기 — 즉시 실행 |
| `propose_replace_line(line_id, text)` | 쓰기 — **제안만** |
| `propose_insert_lines(after_line_id, texts[])` | 쓰기 — **제안만** |
| `propose_delete_lines(line_ids[])` | 쓰기 — **제안만** |
| `propose_replace_document(lines[])` | 쓰기 — **제안만** (초안 생성, 일괄 서식) |

### API 요약

```
상태   /health                         postgres · redis · LLM 도달 여부
계정   /auth/{signup,login,logout,me,password}
세션   /sessions                       목록 · 생성
       /sessions/{sid}                 조회 · 제목변경 · 삭제
       /sessions/{sid}/{open,heartbeat}   점유
대화   /sessions/{sid}/messages        이력 조회 · 전송
       /sessions/{sid}/stream          SSE
문서   /sessions/{sid}/document        조회
       /sessions/{sid}/document/lines[/{lid}]    수정 · 삽입
       /sessions/{sid}/document/lines/delete     삭제 (id 여러 개를 body로)
       /sessions/{sid}/document/export.md        다운로드
       /sessions/{sid}/document/format           일괄 서식 → 제안
       /sessions/{sid}/document/proposal[/accept | /reject]
       /sessions/{sid}/document/{undo,redo}
```

문서는 세션당 하나이므로 **문서 id를 URL에 노출하지 않는다.**
소유자 확인이 `{sid}` 한 곳에서 끝난다.
삭제만 `POST .../lines/delete`인 이유는 `DELETE`에 body를 싣는 취급이
클라이언트·프록시마다 달라 믿을 수 없기 때문이다.

**응답 코드** — 401 미인증 · 403 소유자 아님 · 404 없거나 권한 없음 ·
409 충돌(이메일 중복 · 잠금 · 제안 대기 · 턴 진행 중 · 세션 점유됨) ·
413 요청 초과 · 422 형식 오류 · 503 LLM 도달 실패

### 세션을 여는 순서

```
1. POST /sessions/{sid}/open      점유 등록
2. GET  /sessions/{sid}/stream    SSE 먼저 연결
3. GET  /sessions/{sid}/document  스냅샷
4. GET  /sessions/{sid}/messages  스냅샷
5. 이후 주기적으로 heartbeat      점유 유지
```

**SSE를 스냅샷보다 먼저 연결한다.** 반대로 하면 스냅샷을 받은 뒤 SSE가 붙기까지의 사이에
일어난 변화가 통째로 사라진다. 이벤트가 중복으로 와도 괜찮다 — 같은 상태를 두 번 적용할 뿐이다.
끊기면 마지막 이벤트 id를 실어 다시 붙고, 그마저 만료됐으면 스냅샷부터 다시 받는다.

### SSE

채널은 **세션당 하나**다. 대화와 문서 이벤트가 같은 채널로 온다 —
한 턴 안에서 엮여 일어나므로 채널을 나누면 순서 보장이 깨진다.

`token` · `tool_start`/`tool_end` · `lock`/`unlock` · `proposal` · `proposal_resolved` ·
`document_changed` · `session_meta` · `turn_end` · `error`

- **메아리 방지** — 문서를 바꾸는 요청에 클라이언트 식별자를 실어 보내고 서버가 `origin`으로 되돌려준다.
  프론트는 자기 것이면 무시한다. 안 그러면 자기가 친 글자가 되돌아와 커서가 튄다.
  **적용 버튼을 누른 화면도 마찬가지다** — `proposal_resolved`에도 `origin`이 실린다.
- **잠금의 진실원천은 서버다** — 프론트는 `lock`/`unlock`을 유일한 근거로 삼지 않고,
  잠금 상태일 때 주기적으로 다시 물어 확인한다.

## 스택

프론트 **React + Vite + TypeScript** (시안 Figma) · 백엔드 **Python + FastAPI** ·
LLM **AWS Bedrock** (Claude 계열, 도구 호출) ·
**PostgreSQL** + **Redis** · **Docker**(로컬 개발) · 배포 **AWS**

**인증은 HttpOnly 쿠키 세션** + Redis. 이유는 SSE다 — `EventSource`는 커스텀 헤더를 못 붙이는데
쿠키는 자동으로 실린다. 부수로 토큰이 JS에 노출되지 않고, 서버가 세션을 지울 수 있어
강제 로그아웃과 단일 접속 강제가 즉시 먹는다.

**모델은 바꿀 수 있다.** LLM 클라이언트 인터페이스 뒤에 가둬서 교체가 그 안에서 끝나게 한다.

**모든 반복에 상한이 있다** — 턴당 도구 호출 횟수, 되돌리기 깊이, 요약 재시도.

## 다음에 붙일 것

1차에서 빼되 버리지 않는다. **1차 구조가 둘 다 그대로 받아낸다.**

**민원서 양식** — 문서를 백지가 아니라 정해진 양식에서 시작하게 한다.
LLM의 일이 "글쓰기"에서 **"칸 채우기"**로 바뀐다. 양식은 "섹션 제목 줄 + 내용 줄"이라
**줄 단위 모델이 그대로 적용된다** — 데이터 모델을 바꿀 필요가 없다.
필수 항목이 비면 LLM이 대화로 되묻는다. *먼저 실제 양식을 구해 필수 항목을 확정해야 한다.*

**사진 첨부** — 현장 사진을 올려 민원의 근거로 삼는다. 문서에서는 `![설명](...)` 한 줄이라
**역시 줄 단위 모델 그대로**, 별도 블록 타입이 필요 없다.
`attachment` 테이블과 저장소 추상화(로컬 볼륨 → S3)가 붙는다. 이미지 바이트는 DB에 넣지 않는다.
*한계*: 텍스트 모델은 이미지를 보지 못한다. 파일명과 사용자가 붙인 설명만으로 위치를 판단하므로
배치가 어긋날 수 있고, 제안·승인 구조가 그래서 더 중요해진다.

그 밖에 — 실제 접수처 제출, 이메일 비밀번호 재설정, 비로그인 체험 세션.
