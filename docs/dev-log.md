## [2026-08-27] 요구사항 1차 정리 (브레인스토밍 받아적기)
- **서비스 정의**: 대화하며 LLM과 문서를 만드는 웹 툴. LLM은 문서를 **소유하지 않고 함수(tool call)로 읽고 쓴다.** 사용자가 자유롭게 편집해도 LLM이 항상 최신을 읽는다는 것이 이 설계의 요점.
- **쳐낸 것**: 카카오 연동, 팀 기능, 사용자 맞춤·성향 추론, 테마, 이미지, 세션 간 크로스 참조. "오직 툴" 방향.
- **블록 id 채택**: LLM이 문자 offset으로 위치를 가리키면 사용자가 그 사이 편집한 순간 어긋난다. 안정적 블록 id로 가리켜야 자유 편집과 LLM 수정이 공존한다.
- **편집 잠금(세마포어)**: LLM 쓰기 도구 호출 시 문서를 잠그고 프론트는 블러 + 입력 차단. 턴 종료 시 해제. 실패·연결 끊김에도 영구 잠기지 않도록 타임아웃 필수 — 이걸 수용기준에 넣었다.
- **세션 컨테이너 설계**: 요청마다 Redis에서 복원하는 비상주 컨테이너. 최근 메시지 버퍼 + `context` 요약 문자열을 들고 가고, 버퍼가 차면 absorb LLM이 title/context를 재생성한 뒤 버퍼를 비운다. 사용자가 제목을 직접 정하면 덮어쓰지 않는다.
- 컨테이너는 **문서를 상태로 소유하지 않는다.** 필요하면 tool로 읽는다 → 사용자가 문서를 고쳐도 stale해지지 않는다.
- 수용기준을 M0~M4 마일스톤으로 분해, 전부 테스트·수치로 판정 가능하게 작성.

## [2026-08-27] 편집 제안·승인 모델 도입 · 줄 단위 확정 · 동시 접속 차단
- **LLM에게서 쓰기 권한을 뺐다.** 도구 호출은 제안 버퍼에 쌓일 뿐이고, 문서 코어가 diff(+/−)를 만들어 보여준 뒤 사용자가 **적용**을 눌러야 반영된다. 거절하면 문서는 손대지 않는다.
  - 이 구조 하나로 "LLM이 사용자 편집을 통째로 날린다"는 위험이 원천 소멸한다.
  - 제안 대기 중에는 편집을 잠근다 — 그 사이 사용자가 고치면 제안이 어긋나므로.
  - **적용/거절 결과가 다음 턴 LLM 컨텍스트에 들어간다.** 거절된 걸 또 내밀지 않게. 거절 사유도 선택적으로 전달.
  - **경계 유지**: 문서 코어는 여전히 대화 코어를 모른다. accept/reject 라우트가 두 코어를 각각 호출하고 결과를 대화 코어에 기록한다.
- **블록 = 마크다운 한 줄** 확정. 빈 줄도 블록. diff 단위와 편집 단위가 같아져 계산·표시·되돌리기가 한 좌표계에서 돈다. 붙여넣기 분할 문제도 자동 해소(개행으로 자름).
- **편집 이력 = Redis 스냅샷 스택.** 별도 버전 테이블 없음. LLM 편집 적용 직전 스냅샷은 필수.

  1. 계정당 활성 접속 하나. 새 로그인이 기존 접속을 밀어낸다.
  2. 이미 열린 세션에 접근하면 블러 + "다른 곳에서 작업 중" 읽기 전용.
  LLM 편집 잠금과 같은 오버레이를 재사용하고 사유 문구만 다르게.

## [2026-08-27] 인증·제안 동시성·absorb 실행 확정
- **인증 = HttpOnly 쿠키 세션 + Redis.** 결정 근거는 SSE다. `EventSource`는 커스텀 헤더를 못 붙여서, JWT Bearer로 가면 토큰을 쿼리스트링에 넣거나(URL·프록시 로그에 남음) fetch 기반 스트리밍을 직접 구현해야 한다. 쿠키는 자동으로 실린다. 부수로 XSS에 토큰이 안 새고, 서버가 세션을 지울 수 있어 **단일 접속 강제가 즉시** 먹는다. 대가는 CSRF 대비(SameSite=Lax + 상태변경 요청 보호).
- **살아 있는 제안은 최대 하나.** 제안이 떠 있으면 문서 편집뿐 아니라 **채팅 입력도 막는다.** 이 불변식 하나로 제안 큐·순서·충돌 처리가 통째로 사라진다. 제안 중 `POST /messages`는 409.
- **absorb는 백그라운드.** 턴 응답을 먼저 끝내고 뒤에서 돈다. 완료되면 SSE `session_meta`로 제목을 민다.
  - **실패 처리를 명시**: 실패해도 대화는 멀쩡해야 한다. 기존 title·context 유지, 버퍼도 비우지 않음(다음 기회 재시도). 수용기준에 넣었다.
  - absorb 중 다음 턴이 시작될 수 있으므로 **세션 단위 직렬화** 필요.

## [2026-08-27] 문서 재작성 후 재검토 — 6건 수정
백지 재작성본을 다시 훑어 잡은 것.

- **SQL 예약어 충돌** — `user`와 `order`는 PostgreSQL 예약어다. `SELECT * FROM user`는 `current_user`와 충돌해 에러가 나고, `order`는 쿼리마다 따옴표로 감싸야 한다. `app_user` · `line_order`로 바꿨다. 구현 첫날 걸릴 문제였다.
- **"세션"이 세 가지를 가리키고 있었다** — 대화 스레드, 로그인 상태, 브라우저 연결. "세션 단위 잠금"이 뭘 말하는지 읽는 사람이 알 수 없었다. **용어 표를 두 문서 맨 앞에 넣었다** — 세션(대화 스레드) / 로그인(인증) / 접속(브라우저 연결)로 갈랐다. 팀 문서에서 용어 충돌은 치명적이라 이게 이번 라운드 최대 수정.
- **Redis 키가 문서 id 기준이라 "문서 id 조회가 사라진다"는 주장과 모순** — API는 문서 id를 노출하지 않는데 Redis 키가 문서 id를 쓰면 매 요청마다 sid→doc id 조회가 필요했다. **키를 `doc:{sid}:*`로 바꿔** 문서가 세션당 하나라는 성질을 끝까지 활용했다. 이제 정말로 조회 단계가 없다.
- **read~propose 사이의 경쟁 조건** — 잠금을 첫 `propose`에 걸도록 해뒀는데, LLM이 문서를 읽고 제안을 내기까지 사이에 사용자가 고치면 제안의 기준 문서가 어긋나 엉뚱한 줄이 바뀐다. **잠금을 첫 `read_document()`로 앞당겼다.** 읽었다는 건 관여할 뜻이 있다는 것. 문서를 읽지 않는 순수 대화 턴은 여전히 안 잠기므로 캔버스가 쓸데없이 흐려지지 않는다.
- **세션 제목의 진실원천이 둘** — 요약이 Redis meta만 갱신하면, 세션 목록(Postgres를 읽음)에 옛 제목이 남는다. 요약 완료 시 **Postgres `session.title`을 곧바로 갱신**하도록 명시.
- **`message.role`의 `system`이 LLM API의 system과 헷갈린다** — 제안 처리 결과는 시스템 프롬프트가 아니라 대화 중 사건 기록이다. `note`로 이름을 바꿨다.
- 부수: 회원 탈퇴 시 Redis 정리 누락 보강, `line.updated_at` 제거(전체 덮어쓰기 저장이라 쓸 데가 없다), 대화 이력 복원의 페이지네이션 방향 명시.

## [2026-08-27] 재검토 3라운드 — 설계 결함 5건
표면 문제가 아니라 전부 동작이 틀어지는 것들.

- **한 세션에서 턴이 동시에 두 개 돌 수 있었다.** 409 조건을 "떠 있는 제안이 있으면"으로만 잡아둬서, 응답이 스트리밍되는 도중에 사용자가 메시지를 또 보내면 턴 두 개가 같은 메시지 버퍼를 동시에 고쳐 맥락이 깨진다. **턴 진행 표시(`turn:{sid}:running`)를 두고 세션당 턴 하나로 못박았다.** 턴이 어떻게 끝나든 표시를 지우는 것도 수용기준에 넣었다.
- **diff를 줄 id로 계산하면 전체 재작성 제안이 못 쓰게 된다.** `propose_replace_document`는 모든 줄을 새로 만들므로 id 기준 비교에서는 내용이 그대로인 줄까지 전부 "바뀜"으로 나온다. 사람이 볼 수 없는 diff가 된다. **비교를 줄 내용 기준(LCS 텍스트 diff)으로 명시.**
- **제안이 만든 새 줄에 id가 없었다.** LLM이 줄을 넣고 같은 턴 안에서 그 줄을 다시 고치려면 가리킬 id가 있어야 한다. **임시 id를 즉시 부여하고, 승인 시 확정 · 거절 시 소멸**로 정리했다.
- **세션을 여는 순서에 경쟁 조건이 있었다.** 스냅샷을 먼저 받고 SSE를 나중에 붙이면 그 사이 변화가 통째로 사라진다. **SSE를 먼저 연결하고 스냅샷을 받는 순서**로 못박았다. 중복 이벤트는 무해하다(같은 상태를 두 번 적용할 뿐). 재연결 규약(마지막 이벤트 id, 만료 시 스냅샷 재수신)도 함께 적었다.
- **저장 안 된 작업본이 TTL로 사라질 수 있었다.** "Redis 유실 시 마지막 저장 시점으로 돌아간다"는 감수 사항은 사고를 전제한 것이지, 정상 동작으로 데이터를 버리라는 뜻이 아니다. **dirty인 동안에는 만료를 걸지 않는다**로 명시. 되돌리기 스택도 작업본과 수명을 같이한다.

## [2026-08-27] 전문 통독 감사 — 13건
조각조각 보던 것을 그만두고 641줄을 처음부터 끝까지 통으로 읽었다. 나온 것 전부.

**불일치 (앞선 수정이 문서 전체에 반영되지 않은 것)**
1. ERD 다이어그램은 `user`인데 바로 아래 표는 `app_user` — 예약어 수정이 다이어그램에 안 들어갔다.
2. `read_document()` 반환 필드가 `order` — `line_order`로 통일.
3. 대화 API 주석이 "제안이 떠 있으면 409"만 — 턴 진행 중 조건이 빠졌다.
4. 409 설명 표에도 같은 누락. 413(요청 초과)도 추가.

**설계 구멍**
5. **사용자 편집의 스냅샷 시점이 정의되지 않았다.** 글자마다 남기면 되돌리기 스택이 폭발한다. 편집 시작에 하나 잡고 무입력 저장 시점에 묶음을 확정하는 것으로 정리 — 연속 타이핑은 한 번에 되돌아간다.
6. **heartbeat 끊김을 누가 감지하는지 없었다.** 브라우저가 닫히면 아무도 알려주지 않는다. 주기적 정리 작업이 필요하고, 서버가 여러 대여도 하나만 돌게 잠금을 걸어야 한다. 저장 트리거 "세션 이탈"이 이것 없이는 성립하지 않았다.
7. **`proposal_resolved`에 `origin`이 없었다.** 적용 버튼을 누른 화면도 자기 요청의 메아리를 받는다. `document_changed`에만 달아둔 게 반쪽이었다.
8. **`DELETE .../lines`에 body를 싣는 설계** — DELETE body는 클라이언트·프록시마다 취급이 달라 믿을 수 없다. `POST .../lines/delete`로 바꿨다.
9. **일괄 서식이 턴 흐름 어디에 들어가는지 없었다.** "같은 조건을 받는다"고만 하고 흐름 설명이 없었다. 시작이 버튼일 뿐 같은 흐름을 탄다고 명시.
10. **`GET /health`가 API 목록에 없었다.** 수용기준에서는 쓰는데. LLM이 죽어도 서버는 뜨고 상태만 알려준다는 것도 함께 명시.
11. **가입 시 이메일 중복 응답 코드가 없었다.** 409.

**서술 오류**
12. 7.6에서 "다른 로그인 세션이면 읽기 전용"이라 썼는데, 1번(계정당 로그인 하나)과 겹쳐 읽으면 모순처럼 보였다. 2번이 막는 것은 **밀려난 화면이 그 사실을 알기까지의 시차**와 탭 복제라는 점을 분명히 했다.
13. "잠금 재확인 주기"가 '만들면서 정할 것'에 있었는데 방식은 이미 정해졌고 값만 남았다. '실측 후 정할 값'으로 옮기고, heartbeat 주기·점유 TTL·정리 작업 주기도 함께 넣었다.

## [2026-08-27] 완전 피벗 — UniVoice: 학교별 익명 캠퍼스 민원 서비스
사용자가 첨부 HTML 목업을 기준으로 도메인 자체를 교체했다. 문서 줄 편집 + 제안/승인 모델은
이 서비스와 무관해져서 Kiro spec 3파일(`requirements_v1.md`·`design.md`·`tasks.md`)을 전면 재작성했다.
`docs/`의 Track B(FastAPI+React, 편집형 캔버스) 설계는 손대지 않았다 — 완전히 다른 프로젝트가 됐으므로
더 이상 "같은 원칙의 다른 트랙"이 아니다.

**새 도메인**: 학생이 캠퍼스 시설 불편을 자연어로 제보 → AI가 카테고리 분류 + 행정 문서로 정제 →
학교별로 격리된 익명 게시판에 접수 → 관리자가 상태 처리.

**핵심 결정 (3턴에 걸쳐 확정)**:
1. **학교 격리 방식**: 드롭다운 선택 → 시드된 코드 검증 → 최종 **이메일 도메인 자동 매칭**으로 정착.
   `student@chosun.ac.kr`의 `chosun.ac.kr`로 학교를 자동 판별한다. 드롭다운 오선택 사고 자체를
   원천 차단하고 UI 단계도 줄어든다는 게 이유. 단, 도메인이 같다는 것만으로 관리자가 될 수는 없고
   `admin_codes`(학교별 데모용 임의 코드, 시드 스크립트로만 생성)를 추가로 검증해야 한다.
2. **AI 변환은 원샷이 아니라 대화형.** 위치·상황이 불충분하면 `tool_choice`를 강제하지 않고
   모델이 스스로 "텍스트로 되묻기 vs 도구 호출로 확정"을 판단하게 한다. 강제 호출로 하면
   정보가 없어도 필드를 억지로 채울 위험이 있어서 피했다.
3. **상태 워크플로우를 4단계(접수/수락/보류/거절)에서 6단계로 확장**: 접수 → 확인 → 작업중 →
   수락/보류/거절. 순서 강제 없음, 관리자가 버튼으로 즉시 임의 전환. "누군가 보고 있다/처리
   중이다"를 학생에게 알리는 중간 상태가 필요했다.
4. **철회 기능 추가 + 익명성과의 긴장 해소.** 학생이 접수한 민원을 취소할 수 있어야 하는데,
   완전 무기명이면 "내 글"조차 구분이 안 된다. `submitted_by_user_id`를 내부 전용 컬럼으로 유지해
   (UI에는 절대 노출 안 함) 철회 시 소유권 검증에만 쓴다. 철회 시 비밀번호 재확인을 요구하고,
   철회는 하드 삭제가 아니라 `status='철회'` 전환 — 조회 쿼리에서 항상 제외되지만 레코드는 남는다.
   관리자가 이미 처리했어도 학생은 철회 가능(1차는 단순성 우선, 이 정책은 Out of Scope에 명시).
5. **대화 이력을 `complaint_conversations` 별도 테이블로 분리.** `raw_text` 단일 컬럼 대신
   `draft_key`(접수 전 임시 UUID)로 왕복을 쌓고, 접수 시점에 해당 `draft_key`의 모든 행에
   `complaint_id`를 채워 넣는다. 게시판 "원문 보기"와 관리자 상세 화면 둘 다 이 테이블을 시간순
   렌더링해서 공유한다.

**스키마 변경**: `sessions/messages/documents/lines`(Track A 구버전) 전부 제거.
`schools(email_domain 포함)`, `admin_codes`, `users`, `complaints(status 7종)`,
`complaint_conversations` 5테이블로 교체.

**Out of Scope로 명시한 것**: 이메일 인증/OAuth, 완전 무기명(추적 없는 익명), 실시간 웹소켓,
관리자 다수 권한 등급, 철회 사유 입력, 처리 완료 후 철회 차단 정책.

**영향받은 파일**: `.kiro/specs/complaint-assistant/{requirements,design,tasks}.md` 전면 재작성.
`docs/anonymous_complain_assistant.html`(사용자 제공 목업) 참조 소스로 보존.

## [2026-08-27] 상태 워크플로우 재설계 + DB 스키마/ER 문서화 + 세션 컨테이너 규칙 신설
7단계 중 관리자 쪽 상태를 "미확인 기본값 → 열람 시 자동 확인 → 확인 상태에서만 3지 결정
(수락/보류/거절) → 수락은 처리중을 거쳐야 해결완료 → 보류는 코멘트 필수, 그 외에는 상시 코멘트
가능"으로 구체화했다. 기존 "접수/확인/작업중/수락/보류/거절"은 이름과 전이 규칙 둘 다 부정확했다
— "수락"이 최종 상태처럼 보였는데 실제로는 처리 시작 신호였어야 했다.

**상태명 변경**: 접수→**미확인**, 작업중→**처리중**, 수락(최종)→**해결완료**(수락은 이제 버튼 이름이자
`확인→처리중` 전이 트리거). 최종 목록: 미확인/확인/처리중/해결완료/보류/거절/철회.

**전이 규칙 확정**:
- `미확인 → 확인`은 버튼이 아니라 **관리자가 상세 화면을 여는 행위의 부작용**으로 자동 발생. 별도
  "확인" 버튼은 존재하지 않는다. 감사 목적으로 `complaints.confirmed_at` 컬럼을 추가했다.
- 수락/보류/거절 세 버튼은 **`확인` 상태에서만 노출**된다 (미확인 상태로는 결정 불가 — 관리자가
  안 보고 처리하는 것을 막는 설계).
- **수락은 `처리중`으로만 가고, `해결 완료`라는 별도 버튼을 거쳐야 `해결완료`에 도달**한다. 처리중을
  건너뛴 해결완료 직행은 불가 (DB 레이어에서 `WHERE status='처리중'` 조건으로 차단).
- **보류는 코멘트가 필수.** 버튼 클릭 시 작은 모달이 뜨고 텍스트를 입력해야만 실제 전환이 일어난다.
  DB에서는 상태 전환(`UPDATE complaints`)과 코멘트 생성(`INSERT complaint_comments`)을 **하나의
  트랜잭션**으로 묶어, 전환이 실패하면 코멘트도 안 남게 했다.
- **코멘트는 상태와 무관하게 언제든 추가 가능한 누적 로그.** 단일 컬럼(`hold_reason` 같은)이 아니라
  `complaint_comments` 별도 테이블로 분리했고, `is_hold_reason` 플래그로 "보류 전환 시 필수로 남긴
  것"과 "그 이후 자유 코멘트"를 구분한다.

**DB 레이어 설계 결정**: 기존의 만능 메서드 `update_complaint_status(id, school_id, new_status)`
하나를 없애고 `confirm/accept/resolve/hold/reject_complaint` 5개로 쪼갰다. 각 메서드가 자기
선행 상태를 `WHERE status = '<선행>'`에 박아 넣어서, **전이 규칙 자체가 DB 쿼리 조건으로 강제**된다.
순서를 건너뛴 호출은 UI가 버튼을 안 보여줘서 정상 흐름에선 안 나지만, 여러 관리자가 동시에 같은
민원을 조작하는 경쟁 상황의 방어선으로 남긴다.

**DB 스키마·관계 재문서화**: requirements.md·design.md 양쪽에 ER 관계도(텍스트 다이어그램)와
카디널리티·삭제전파 표를 추가했다. 핵심 결정: `submitted_by_user_id`(민원→작성자)와
`author_user_id`(코멘트→작성 관리자)만 `ON DELETE SET NULL`, 나머지(schools→하위 전체)는
CASCADE. 민원·코멘트 내용은 학교의 공공 기록이라 작성자 탈퇴와 무관하게 보존해야 한다는 게 근거.

**세션 컨테이너 규칙 신설**: 두 문서에 새 섹션을 추가해 Streamlit `st.session_state`(탭 단위,
휘발성)와 DB(영속)의 경계를 표로 명시했다. 세션에 두는 것은 인증 3종·`draft_key`·미리보기·
`selected_complaint_id`·모달 임시 입력값뿐이고, 대화·목록·통계·코멘트·**상태 자체**는 절대
세션에 캐시하지 않고 매번 DB에서 재조회한다. 특히 `미확인→확인` 자동전환은 "세션 값이 바뀌는
게 아니라 그 세션 값을 세팅하는 요청 안에서 DB를 갱신하는 것"이라고 명시해, 새로고침해도 확인
처리가 풀리지 않음을 보장했다.

**tasks.md M4 재구성**: TASK-401(DB 전이 메서드)~TASK-407(코멘트 상시 입력)까지 7개로 세분화.
기존 "확인/작업중/수락/보류/거절 5버튼 상시 노출" 방식의 태스크는 폐기.

**영향받은 파일**: `.kiro/specs/complaint-assistant/{requirements,design,tasks}.md` 상태

  - **`dev-log.md`는 이름을 그대로 뒀다.** 이건 v1의 산출물이 아니라 프로젝트 내내 이어지는 기록이라 버전을 붙일 대상이 아니다. (한 번 `_v1`을 붙였다가 되돌렸다.)
- **`docs/api-contract.md` 신규.** 프론트(JS)와 백엔드(FastAPI)가 서로를 기다리지 않고 각자 만들기 위한 계약서. `.kiro` 정본의 기능을 HTTP 경계로 옮긴 것이다.
  - 연결부 22개를 네 묶음(인증 7 · 작성 4 · 게시판 4 · 관리자 7)으로 정리하고, 각각 프론트 함수명 ↔ HTTP ↔ 백엔드 함수 ↔ 서비스 계층을 한 줄에 붙였다.
  - **설계 판단 몇 가지를 규약에 못박았다:**
    - `school_id`를 프론트가 보내지 않는다 — 서버가 세션에서 꺼내 강제 필터링. 프론트 코드에 학교 분기가 하나도 안 생긴다.
    - `is_mine`을 서버가 계산해 내려준다 — 익명이라 작성자 id를 못 보내는데 프론트는 "내 글" 여부를 알아야 한다. 서버만 아는 사실이라 불린 하나로 답한다.
    - **상세 열람이 `POST`다.** 조회처럼 생겼지만 미확인→확인 전환이라는 부작용이 있어서, `GET`으로 두면 브라우저·프록시의 프리페치로 열지도 않은 민원이 확인 처리된다.
    - **`submit`에 확정안을 싣지 않는다.** 프론트가 보낸 값을 저장하면 화면에서 값을 바꿔 보낼 수 있게 된다. 서버가 그 draft의 마지막 결과를 쓴다.
    - **`submit` 응답에 `next_draft_key`를 함께 준다.** 접수 후 다음 민원이 앞 대화와 섞이지 않도록 서버가 새 키를 바로 발급한다. 프론트가 별도 호출을 하지 않는다.
    - 수정 전용 API를 만들지 않았다 — 미리보기 상태에서도 같은 `messages` 엔드포인트를 쓴다. 대화가 곧 수정 수단이다.
  - 상태 전이 규칙을 **프론트와 서버 양쪽에 적었다.** 중복처럼 보이지만 프론트는 "보여줄 것을 고르는 것", 서버는 "일어날 일을 정하는 것"이라 목적이 다르다. 화면에서 감추는 건 편의이고 막는 건 서버다.
  - 오류 문구를 서버가 만들고 프론트는 `error.message`를 그대로 표시하게 했다. 문구가 두 곳에 흩어지면 관리가 안 된다.
- 합의 대기 5건을 문서 끝에 남겼다 — 페이지네이션, 실시간 반영 방식(새로고침 vs 폴링), 재대화 시 미리보기 교체, 비밀번호 정책, Bedrock 타임아웃.
- **UI 시안(`anonymous_complain_assistant.html`) 대조 결과를 계약서 8장에 추가.** 시안은 `.kiro` 정본보다 앞선 버전이라 그대로 옮기면 어긋난다.
  - **상태값이 가장 크게 다르다**: 시안 4개(접수/수락/거절/보류) vs 정본 7개(미확인/확인/처리중/해결완료/보류/거절/철회). 특히 시안의 `수락`이 최종처럼 보이지만 정본에서는 `처리중`일 뿐이고 `해결완료`를 한 번 더 거친다.
  - 시안에 아예 없는 것: 로그인·가입, 학교 격리, AI 되묻기(시안은 한 번에 끝남), 철회, 코멘트, 자동 확인 전환.
  - 시안에 있지만 다르게 가는 것: `switchView()` 학생/관리자 전환 버튼 → 실제로는 `role` 기반이라 버튼을 만들지 않는다. `rawText` 단일 문자열 → 대화 왕복 배열.
  - 그대로 가져가는 것: 관리자 표 컬럼 구성이 정본과 맞는다. 상세 모달·배지·필터 탭·통계 카드·토스트도 구조는 유지 — 바뀌는 건 값과 개수이지 구성이 아니다.
  - `feedCount`는 별도 API를 두지 않고 목록 길이를 쓴다. 관리자 통계만 상태별 집계라 목록으로 안 나와서 따로 받는다.
- **계약서를 함수 단위 상세로 확장** (172줄 → 900줄대). 이름만 매칭한 표로는 각자 만들 수 없다는 지적을 받아, 22개 연결부 전부에 대해 다음을 박았다.
  - **프론트 JS 시그니처**(JSDoc 주석 포함)와 **백엔드 FastAPI 시그니처**(타입 힌트·의존성 주입)를 나란히
  - **파라미터 표** — 이름·타입·필수 여부·설명
  - **건드리는 테이블** — 읽기(R)/쓰기(W)/삭제(D)까지. 한눈 표에도 컬럼으로 넣었다
  - **하는 일과 그렇게 정한 이유** — 판단이 필요한 곳만
  - 실제 SQL 조건(`WHERE status='확인'` 등)을 코드 블록에 그대로 적었다. 전이 검증이 조회 후 판정이 아니라 UPDATE의 WHERE 절이라는 게 중요해서 — 동시에 두 관리자가 눌러도 하나만 성공한다.
  - `client.js`를 실제 구현 수준으로 적었다. 22개 함수가 각자 `credentials`를 붙이면 하나는 반드시 빠뜨리므로 한 곳에 모은다. 도메인 모듈은 그 위에 한 줄씩 얹는 형태로 예시를 넣었다.

## [2026-08-27] 계약서 검증 — 6건, 그중 하나는 구현 불가능
`.kiro` 정본에 대고 계약서를 전수 대조했다. User Story 34개, 테이블 6개, 상태 7개, 카테고리 7개.

**치명 — 접수가 구현 불가능했다**
- `submitDraft`에서 "서버가 그 draft의 마지막 확정안을 쓴다"고 적었는데, **서버는 확정안을 저장하지 않는다.** 정본 스키마에서 AI 발화는 `content`에 `"[정리 완료] {제목}"` 문자열로만 남고 `category`·`location`·`refined_body`가 어디에도 없다. 내가 쓴 `service.last_refined(draft_key)`는 존재할 수 없는 함수였다.
  - 정본(Streamlit)은 `st.session_state['preview_result']`에 들고 있다가 `submit(..., refined)`로 넘긴다. 세션이 서버 메모리라 가능했던 것인데, HTTP 경계에서는 그 세션이 브라우저에 있어서 같은 방법을 쓰면 값을 위조할 수 있다.
  - **해결: `complaint_conversations.refined_json TEXT` 컬럼 추가.** 확정 턴에 JSON을 함께 저장하고 접수 때 마지막 것을 꺼낸다. 이 컬럼이 `is_complete` 표시도 겸한다 — `NOT NULL`인 행이 없으면 아직 확정 전이라 409.

**누락 — 대회 심사 기준이 빠져 있었다**
- **US-5.1(Bedrock 호출 로그)에 대응하는 API가 없었다.** 심사위원이 확인하는 항목인데 계약서에 없었다. `GET /admin/bedrock-logs` + `bedrock_logs` 테이블을 추가했다.
  - **프롬프트·응답 본문은 저장하지 않는다.** 민원 내용이 로그에 중복 보관되면 익명성 관리 대상이 두 곳이 된다. 심사에 필요한 건 호출이 일어났다는 사실과 지연·토큰이지 내용이 아니다.

**요구사항 미충족**
- **US-3.6**("관리자 코멘트, 특히 보류 사유를 게시판에서도 확인")을 목록 응답이 만족하지 못했다. `comments`를 빈 배열로 두고 상세에서만 채우게 했는데, 학생 화면은 카드 목록이라 상세를 따로 열지 않는다. → 목록에는 `is_hold_reason=1`인 것만 싣는다. 전부 실으면 응답이 무거워진다.
- **`is_mine`을 목록에서 계산하는 처리가 빠져 있었다.** 철회 버튼이 게시판 카드에 붙으므로 목록에도 필요하다.

**정본과 불일치**
- `get_conversation`에 `complaint_id IS NULL` 조건을 적었는데 정본은 `WHERE draft_key=?`만이다. 정정.

**구조적 한계 (1차 수용)**
- **`draft_key`는 소유권 검증이 불가능하다.** `complaint_conversations`에 `user_id`가 없어서 남의 키를 알면 초안 대화를 읽고 이어 쓸 수 있다. uuid4라 추측은 사실상 불가능하지만 구조적으로 막혀 있진 않다. 초안은 접수 전 임시 데이터라 1차에서는 이대로 가되, 막으려면 `owner_user_id`가 필요하다는 것을 명시했다. 접수된 민원은 정상 보호된다.

**커버리지 표를 9장에 추가.** US 34개 중 API로 덮이지 않은 것은 US-4.8(게시판 즉시 반영) 하나이고, 갱신 방식(새로고침 vs 폴링)을 안 정해서다.

## [2026-08-27] Streamlit 제약 해제 — 8501에 일반 웹서버
**대회 가이드를 다시 읽어 Streamlit이 요건이 아님을 확인했다.** 가이드가 함께 받은 코드(`app.py` 등 5개)를 "인프라와 Kiro 연동이 정상 동작하는지 확인하기 위한 **예시/테스트 코드**"라고 명시한다. 8501은 그 예시를 띄우라고 알려준 포트이고, 보안그룹에서 열리는 건 포트 번호지 거기 무엇이 뜨는지가 아니다.

**결정: 8501에 FastAPI + uvicorn을 올린다.**
```
uvicorn app.main:app --host 0.0.0.0 --port 8501
```

**이 판단으로 Streamlit 제약 세 가지가 통째로 사라진다.**
1. **새로고침 시 로그인 유실** — `st.session_state`는 웹소켓 연결 단위라 F5에 초기화된다. 쿠키 컴포넌트나 URL에 세션 id를 싣는 우회책이 필요했다. HttpOnly 쿠키를 쓰면 문제 자체가 없다.
2. **서버에서 클라이언트로 밀어주기 불가** — 폴링밖에 없었다. SSE가 그대로 된다.
3. **상호작용마다 스크립트 전체 재실행** — 매 클릭마다 목록·통계 재조회. 없어진다.

**이중 트랙(Track A/B)이 사라졌다.** 그 구조는 "Streamlit이 제약이라 대회용과 확장용을 나눠야 한다"는 전제에서 나온 것인데, 전제가 틀렸으므로 나눌 이유가 없다. `KIRO_SPEC.md`를 트랙 없는 단일 구조로 다시 썼다.

**`api-contract.md` 954줄이 가정 없이 그대로 적용된다.** Streamlit용 "함수 계약"으로 다시 쓸 필요가 없어졌다.

**프로세스도 준다.** FastAPI가 정적 파일까지 서빙하면 8501 하나에 프로세스 하나다. Streamlit + FastAPI + Redis 셋을 띄우는 것보다 단순하다.

**검증에서 나온 `refined_json` 컬럼은 여전히 필요하다.** Streamlit이었다면 확정안이 서버 메모리(`st.session_state`)에 있어 위조가 불가능했지만, HTTP 경계에서는 그 자리가 브라우저다. 서버가 확정안을 저장해야 한다.

**고친 문서**
- `.kiro/requirements.md` — 제약 항목에서 프론트엔드 제거, 8501 명시. Session Container Rules를 서버 세션 기준으로 재작성(새로고침을 견딘다는 점이 이전 판과 결정적으로 다름)
- `.kiro/design.md` — 아키텍처 도식, 파일 구조, UI Design 절 제목, Next Steps
- `.kiro/tasks.md` — `requirements.txt` 의존성, 실행 명령, `deploy.sh`의 nohup 구문
- `KIRO_SPEC.md` — 트랙 없는 단일 구조로 전면 재작성. 구현 시작점을 `api-contract.md`로 명시
- `docs/*_v1.md` — 배너에서 트랙 서술 제거, "v1 설계이고 현재 정본은 .kiro"로 정리

**남은 것**: HTTPS가 없으면 쿠키에 `Secure`를 못 단다. EC2 IP로 http 접속이면 `SameSite=Lax`로 가고 데모 범위에서 감수한다.

## [2026-08-27] 표준 웹서버 구성으로 재편 — PostgreSQL + Redis + 워커 여러 개
Streamlit 제약이 풀리면서 아키텍처를 흔한 웹 서버 형태로 다시 잡았다. **중앙 데이터스토어 + 백엔드 워커 N개.**

**왜 워커를 여럿 두나**: LLM 호출이 수 초씩 걸린다. 워커가 하나면 한 사람이 민원을 정제하는 동안 다른 사람의 게시판 조회까지 막힌다. 심사위원 여러 명이 동시에 만지는 데모에서 이건 그대로 드러난다.

**그 결정이 나머지를 전부 정했다.** 워커가 여럿이면 프로세스 메모리에 상태를 둘 수 없다 — 다음 요청이 다른 워커로 가기 때문이다.
- **세션 → Redis.** 메모리에 두면 요청마다 로그인이 풀렸다 붙었다 한다.
- **SQLite → PostgreSQL.** 파일 락에 기대는 구조로는 여러 프로세스가 동시에 못 붙는다.
- **전이 검증 → `UPDATE ... WHERE status=<전제>`.** 조회 후 판정하면 두 관리자가 동시에 눌렀을 때 각자 다른 워커에서 같은 값을 읽어 둘 다 통과한다. WHERE에 넣으면 DB가 직렬화한다.
- **목록·통계·코멘트는 어디에도 캐시하지 않는다.**

**DB 선택 — MySQL로 썼다가 PostgreSQL로 돌렸다.** 사용자가 "redis mysql이든"이라 한 걸 그대로 받아썼는데, 이 프로젝트엔 Postgres가 맞다. `refined_json`이 JSON 컬럼이고 접수 경로의 핵심인데 `JSONB`는 이진 저장이라 `refined_json->>'category'`로 필드를 직접 읽는다. v1 문서도 이미 PostgreSQL이었다. 스키마 전체를 PG 문법으로 옮겼다(`SERIAL`·`TIMESTAMPTZ`·`CHECK` 제약·`JSONB`·테이블 밖 `CREATE INDEX`).

**Redis는 부활한 것이다.** v1(FastAPI+React)에 세션·작업본 저장소로 있다가, Streamlit으로 가면서 `st.session_state`가 그 역할을 대신해 스택에서 빠졌었다. Streamlit을 걷어내니 그 자리가 다시 빈다.

**초안 소유권을 Redis가 쥔다.** 검증에서 "`draft_key`는 소유권 검증이 구조적으로 불가능하다"고 남겼던 항목이 해소됐다 — `draft:{key}:owner`를 두고 draft 엔드포인트마다 세션과 대조한다. `complaint_conversations`에 영속 컬럼을 늘리지 않은 이유는 초안이 접수 전 임시 데이터라 Redis의 수명과 맞기 때문이다.

**CORS가 사라졌다.** FastAPI가 정적 프론트까지 서빙하므로 동일 출처다. `app.mount`는 API 라우터 **뒤에** 등록해야 한다 — 순서가 바뀌면 `/api/...`가 정적 핸들러에 먹힌다.

**고친 문서**: `.kiro`의 requirements(제약·스택·아키텍처 도식·상태 저장 규칙·스키마 전체)·design(도식·커넥션·AuthManager·UI 흐름)·tasks(의존성·실행·배포), `KIRO_SPEC.md`, `docs/api-contract.md`(아키텍처 전제·Redis 키·소유권 검증·동시성 근거·백엔드 계층·미결 항목).

**루트 중복 파일 정리.** 팀원이 `connectionTest/`의 파일 6개를 저장소 루트에도 push했는데, 루트 쪽은 `BUCKET_NAME = "your-team-bucket-name-here"` 플레이스홀더 원본이고 `connectionTest/`에 실제 값(`hackathon-e1-t01-docs`)이 들어 있었다. 대회 가이드가 경고한 "새 코드가 실제 값을 플레이스홀더로 덮어쓰는" 상황이라, 루트 사본을 지웠다. 잃는 내용 없음.

## [2026-08-27] 계약서 재검증 — 7건
아키텍처가 PostgreSQL+Redis 다중 워커로 바뀐 뒤 다시 훑었다.

**보안 구멍 1건**
- **`getDraftConversation`에 소유권 검사가 빠져 있었다.** 쓰기(#9)와 접수(#11)에는 `require_draft_owner`를 붙였는데 읽기(#10)에는 안 붙였다. 남의 `draft_key`를 알면 그 초안 대화를 통째로 읽을 수 있었다. 읽기도 검사한다.

**동시성 1건**
- **한 초안에서 턴이 여러 개 돌 수 있었다.** 응답 전에 또 보내면 Bedrock 호출이 둘 다 돌고 대화 순서가 꼬인다. `draft:{key}:running`을 `SET NX`로 세워 막는다. **`nx=True`가 핵심** — 워커가 여럿이라 "있는지 보고 세우기"로 하면 두 워커가 동시에 통과한다. `ex`로 만료를 줘서 워커가 죽어도 표시가 영원히 남지 않게 했다.

**정의 안 된 것 5건**
- **TTL 정책**: 세션은 요청마다 연장(sliding), 초안은 발급 시점부터 고정. 민원을 길게 쓰는 도중 로그아웃되면 안 되고, 미접수 초안은 버려도 되는 데이터다. 만료된 초안 키는 `404 DRAFT_NOT_FOUND` → 프론트가 새 초안을 시작한다.
- **역할 경계 전체**를 표로. 특히 **관리자는 초안·작성 API를 못 쓴다(403)** — 민원을 넣는 것은 학생의 일이다. 한 계정이 두 역할을 겸하지 않는다.
- **철회된 민원의 직접 조회**: 목록에서만 빼면 링크를 아는 사람에게는 계속 보인다. `db.get_complaint`에 `status <> '철회'`를 넣어 목록·상세·원문·관리자 상세를 전부 막는다.
- **입력 검증 규칙**을 표로 (이메일 형식·비밀번호 8자·메시지 2000자·코멘트 1000자 등). 길이 상한은 본문 크기 제한(413)과 별개로 400이다.
- **SPA 라우팅 fallback**: `/board/12`에서 새로고침하면 404다. `html=True`는 없는 경로까지 덮지 않는다. 해시 라우팅이나 catch-all 중 하나를 골라야 한다 — 데모라면 해시 라우팅이 설정이 없어 낫다.

한눈 표의 "건드리는 것" 칸도 Redis 접근을 반영해 갱신했다.

## [2026-08-27] 계약서 3차 검증 — 프론트가 화면을 만들 때 필요한 것 기준
이번엔 "프론트 개발자가 이 문서만 보고 화면을 만들 수 있나"로 훑었다.

- **오류 코드 표가 없었다.** 프론트가 `error.code`로 분기한다고 규약에 적어놓고, 정작 코드가 본문 15곳에 흩어져 있어 목록을 알 수 없었다. **16개를 표 하나로 모으고** 각각에 대해 "프론트가 할 일"까지 붙였다.
  - 그중 넷(`FORBIDDEN_ROLE`·`DRAFT_NOT_COMPLETE`·`TURN_IN_PROGRESS`·`HOLD_REASON_REQUIRED`)은 **프론트가 이미 막았어야 하는 것**이라고 표시했다. 받았다면 화면 상태가 서버와 어긋난 것이므로 조용히 삼키지 말고 다시 받아오라고 적었다.
  - **0장 예시가 실재하지 않는 코드(`COMPLAINT_NOT_CONFIRMED`)를 쓰고 있었다.** 실제 코드는 `INVALID_TRANSITION`이다. 문서 첫 예시가 틀린 코드였다.
  - `EMAIL_TAKEN`을 400으로 적은 곳과 409로 적은 곳이 있었다. 409로 통일.

- **갱신 규칙이 없었다.** "목록·통계를 캐시하지 않는다"는 원칙만 있고 **언제 다시 받을지**가 없어서, 상태를 바꾼 뒤 화면에 옛 숫자가 남는다. 행동별 재조회 표를 3-1장으로 추가했다.
  - **응답을 쓰는 것과 다시 받는 것을 구분**했다. 상태 변경 API는 갱신된 `Complaint`를 돌려주므로 상세는 갈아끼우면 되고 목록·통계만 따로 받는다.
  - `getStats`는 상태가 바뀔 때만 받는다 — 상태별 집계라 전이가 없으면 변할 일이 없다.

- **`Complaint.comments`의 의미가 목록과 상세에서 다른데 타입이 같았다.** 목록엔 보류 사유만, 상세엔 전부 담긴다. 타입만 보면 구분이 안 돼서 카드에서 "코멘트 N개"를 세면 틀린다. 경고를 타입 바로 옆에 붙였다.

- **앱 진입·로그아웃 흐름이 없었다.** `getMe()`를 가장 먼저 부르고 role이 화면 전체를 정한다는 것, 로그아웃 시 무엇을 버리는지(특히 `draft_key`를 재사용하지 않는다는 것), 탈퇴도 같은 정리를 한다는 것을 4-1장으로 추가했다.

- `client.js`도 고쳤다. 401을 무조건 로그인 화면으로 보내고 있었는데, `WRONG_PASSWORD`·`INVALID_CREDENTIALS`도 401이라 비밀번호를 한 번 틀리면 로그아웃되는 동작이었다. **`UNAUTHENTICATED`일 때만** 가로채도록 코드로 가른다.

## [2026-08-27] 최신 시안(full_schools) 대조 — 학교 목록 API 누락 발견

## [2026-08-27] 가입 화면 확정 — 드롭다운 + 교직원 토글
실제 화면 정의를 받아 정본과 계약을 맞췄다.

**화면**
- 로딩 → 로그인(이메일·비밀번호·로그인·회원가입) → 회원가입(학교 드롭다운·이메일 아이디·비밀번호·교직원 여부 토글·(토글 시) 학교 코드)

**바뀐 것**
- **학교 드롭다운 채택.** 초기 정본은 "이메일 전체를 입력하면 도메인으로 학교 자동 매칭, 선택 UI 없음"이었다. 그 근거가 "목록에서 실수로 다른 학교를 고르면 민원이 잘못된 게시판에 올라간다"였는데, **드롭다운은 고르는 순간 도메인이 잠기므로 그 사고가 생기지 않는다.** 오히려 오타가 원천 차단되고 지원 학교를 처음부터 볼 수 있다. US-1.1·1.3 재작성.
- **역할 선택 → 교직원 여부 토글.** 학생/관리자 라디오가 아니라 토글이고, 켜면 코드 칸이 펼쳐진다. API는 `is_staff: bool`을 받아 서버가 `role`로 옮긴다(`true` → `admin`). 화면 용어는 "교직원", DB는 `role`. US-1.2 재작성.
- **`schools.aliases TEXT[]` 추가.** "조대"·"지스트"로 검색되지 않으면 드롭다운이 쓸모없다.

**바뀌지 않은 것 — 학교를 정하는 근거는 여전히 도메인 하나다.** 프론트가 보낸 학교 이름을 서버가 믿지 않고, 조립된 이메일의 도메인으로 다시 조회해 확정한다. 드롭다운은 입력 편의일 뿐 판정이 아니다. 그래서 `signup`의 서버 로직이 그대로다.

**계약서에 화면↔API 대응표(4-0)를 추가했다.** 화면 요소마다 무엇을 부르는지, 부르지 않는지(토글은 화면 상태일 뿐 API 없음)를 적었다. 가입 성공 시 `Set-Cookie`가 함께 내려와 **다시 로그인하지 않는다**는 것도 명시.

**로딩 화면의 정체**: `getMe()` 응답을 기다리는 시간이다. role을 알기 전에는 학생 화면인지 관리자 화면인지 정할 수 없어 아무것도 못 그린다.

## [2026-08-27] UI 시안(full_schools)을 확정 설계에 맞춰 수정
목업 시뮬레이터 수준에서 화면만 맞췄다. 실제 API 연동은 없다.

**가입 화면**
- 학생/시설관리자 라디오 → **교직원 여부 토글**. 회원가입 모드에서만 보이고, 켜면 **학교 코드 입력칸이 펼쳐진다**. 로그인으로 돌아가면 토글이 꺼지고 코드칸도 닫힌다.
- 학교 드롭다운(검색·별칭)과 도메인 자동 부착은 그대로 뒀다 — 확정된 방식이다.

**상태 4종 → 7종**
- `접수/수락/거절/보류` → `미확인/확인/처리중/해결완료/보류/거절/철회`. 배지 색을 여섯 개 정의했다(철회는 화면에 나타나지 않으므로 색이 없다).
- 관리자 필터 탭도 6종으로.
- 통계 카드는 라벨 위치를 유지하되 집계 기준을 새 상태로 옮겼다.

**상태 전이 규칙을 화면에 반영**
- **상세를 열면 미확인 → 확인으로 자동 전환된다.** 확인 버튼은 만들지 않았다 — 열람 자체가 확인 행위다. 전환 시 토스트로 알린다.
- **결정 버튼은 `확인` 상태에서만 보인다.** `미확인` 행에는 "열람하면 결정할 수 있습니다"가 뜬다.
- **수락은 `처리중`까지만.** 그 뒤 `처리중` 상태에서만 "해결 완료" 버튼이 나온다. 두 단계를 건너뛸 수 없다.
- 최종 상태(`해결완료`·`거절`·`보류`)에는 결정 버튼이 없다.

**새로 붙인 화면**
- **보류 사유 모달** — 텍스트가 비면 버튼이 비활성이다. 사유 없이는 보류가 성립하지 않는다는 규칙을 UI로 강제했다. 남긴 사유는 게시판 카드에도 노란 박스로 표시된다(US-3.6).
- **코멘트 모달** — 상태와 무관하게 언제든 열린다. 누적되고, 보류 사유는 강조 표시로 구분한다.
- **철회 모달** — 비밀번호 확인. 본인 글(`isMine`)에만 버튼이 보인다.
- **로딩 화면** — 진입 시 스피너. 실제로는 `getMe()`를 기다리는 시간이다.

**철회 처리**: 하드 삭제가 아니라 상태 전환이고, 게시판과 관리자 표 **양쪽 필터에서 제외**했다.

`isMine`·`comments`를 민원 객체에 추가했다. 실제로는 서버가 세션과 대조해 내려주는 값이라는 주석을 달았다.

**남겨둔 것**: `parseNaturalInput()`·`guessCategory()`가 브라우저에서 카테고리를 추측하는 부분은 그대로다. 시뮬레이터라 Bedrock이 없어서 대체할 게 없다 — 실제 구현에서는 서버가 주는 값이라는 것을 계약서 8장에 적어뒀다.

| 코드 칸 | 결과 |
|---|---|
| 비어 있음 | `student`로 가입 |
| 그 학교 코드와 일치 | `admin`으로 가입 |
| 넣었는데 안 맞음 | `400 INVALID_ADMIN_CODE` — 가입 자체가 막힌다 |

**틀린 코드를 조용히 학생으로 강등시키지 않는다.** 그러면 사용자는 관리자로 가입된 줄 알고 관리자 화면을 찾다 헤맨다. 막고 알리는 쪽이 맞다. 시안의 교직원 토글도 없애고 **선택 입력칸 하나**로 바꿨다.

`signup` 응답에 `role`을 추가했다 — 가입 직후 어느 화면으로 갈지 프론트가 알아야 한다.

**경고를 화면에 붙였다.** 각 오류가 어느 칸 아래에 무엇을 띄우는지 계약서에 표로 박고 시안에 구현했다.
- 이메일 중복 → "이미 가입된 이메일입니다" + **로그인 링크**
- 코드 불일치 → "유효하지 않은 코드입니다. 비워두면 학생으로 가입됩니다"
- 비밀번호 8자 미만 → 비밀번호 칸 아래
- 미등록 도메인 → 이메일 칸 아래 + 지원 학교 보기

**철회 흐름을 세 단계로 명확히 했다.**
1. 경고창 — "즉시 사라지고 **되돌릴 수 없습니다**" + 비밀번호 칸
2. 비밀번호 불일치 → **창을 닫지 않는다.** 칸을 비우고 경고를 띄우고 포커스를 되돌린다. 처음부터 다시 여는 건 사고에 가깝다
3. 일치 → 창을 닫고 **"삭제되었습니다"** 알림 → 목록에서 사라진다

**접수에 확인창을 넣었다.** "정식 접수"가 곧바로 올라가지 않고 "이대로 접수하시겠습니까?"가 뜬다. 취소하면 아무것도 부르지 않고 미리보기가 남아 계속 고칠 수 있다. 게시판에 공개되는 동작이라 한 번 더 묻는다.

시안에 데모용 서버 상태를 넣었다 — `adminCodeDB`(학교별 코드), `registeredEmails`(중복 검사), `currentPassword`(철회 재확인). 실제로는 각각 `admin_codes` 테이블·`users` 테이블·서버 해시 대조라는 주석을 달았다.

## [2026-08-27] 삭제 흐름을 세 단계로 · `verifyPassword` 신설
철회를 **경고+비밀번호 → 최종 확인 → 실행** 세 단계로 나눴다.

**`POST /auth/verify-password`(#7-1)를 새로 만들었다.** 기존에는 철회 API 하나뿐이라 비밀번호가 틀렸다는 걸 "정말 삭제하시겠습니까?"를 지난 **뒤에야** 알 수 있었다. 순서가 뒤집혀 있었다 — 삭제를 결심하고 확인을 누른 다음에 비밀번호 오류를 만나면 결심을 두 번 하게 된다.

이 엔드포인트는 **아무것도 바꾸지 않는다.** 조회만 하고 204/401을 돌려준다. 그리고 **실행 API가 비밀번호를 다시 받아 검증한다** — 1단계는 화면 흐름을 위한 것이지 실행 권한을 주는 것이 아니라서, 건너뛰고 철회를 직접 불러도 서버가 막는다.

**탈퇴도 같은 흐름을 탄다.** 되돌릴 수 없는 정도가 더 크므로 경고 문구만 더 분명히 한다. 계약서에 "되돌릴 수 없는 동작의 공통 흐름" 표로 묶었다.

**시안 구현에서 걸린 것**: `closeWithdrawModal()`이 `withdrawTargetId`를 지우고 있어서 1단계 창을 닫고 2단계로 넘어가면 대상을 잃었다. 닫기와 취소를 분리해 **[취소] 버튼만 타깃을 지우도록** 했다.

접수 확인창도 US-2.7에 반영했다. 새 수용기준 셋 추가 — 접수 취소 시 접수 안 됨, 비밀번호 틀리면 확인창으로 안 넘어감, 맞으면 확인창을 거쳐야 삭제됨.

미결에 `verifyPassword` 실패 횟수 제한을 추가했다. 비밀번호를 무제한 시도할 수 있으면 안 된다.

## [2026-08-27] 계약서에서 구현을 걷어내고 `backend-design.md` 신설
**계약서가 파사드 문서가 아니게 돼 있었다.** SQL 21개, `db.*` 호출 30개, `redis.setex`, 트랜잭션 경계까지 들어가 있었다. 그건 서버 안쪽 이야기지 프론트와 백엔드가 합의할 경계가 아니다. **내부 구조를 바꾸면 계약서를 고쳐야 하는 상태**였고, 그러면 갈라 둔 의미가 없다.

**`docs/backend-design.md`(886줄) 신설.** 모듈 분해와 안쪽 흐름 전부를 옮기고 새로 채웠다.
- **라우터는 파사드다** — 파싱·세션 꺼내기·직렬화만. 판단이 없다. 라우터에 `if`가 늘면 서비스로 내려가야 할 로직이다.
- 계층 규칙 여섯 개를 표로 (`SQL은 repo에만`, `Redis 키는 session에만`, `Bedrock은 llm에만`, `환경변수는 config에서만` 등). import 그래프 테스트로 강제한다.
- **`school_id` 격리를 repo가 강제한다** — 모든 조회 함수가 `school_id`를 필수 인자로 받는다. 안 넘기면 호출 자체가 안 된다. 서비스마다 손으로 `WHERE`를 붙이면 언젠가 하나를 빠뜨린다.

**사용자가 물은 것들을 채웠다.**
- **계정 저장·로그인 검증**: bcrypt 해시, 계정이 없을 때도 더미 해시를 대조하고 401 — 응답 속도로 이메일 존재 여부가 새는 것을 막는다. "이메일 없음"과 "비밀번호 틀림"을 구분하지 않는다.
- **세션 복원 경로**: 요청마다 쿠키 → Redis 조회. `school_id`·`role`을 세션에 넣어둬 PostgreSQL을 안 건드린다. 대가는 권한 변경이 기존 세션에 안 먹힌다는 것 — 그 기능이 없으니 지금은 무해하다고 적었다.
- **대화 세션 컨테이너 3단계**(세션 목록 / 세션 메타 / 대화 기록). **`.kiro`에 이 개념이 아예 없었다** — `chat_sessions` 테이블을 제안하고 정본 반영이 필요하다고 표시했다.
- **'부족하다' 판정**: 이게 제일 큰 설계 변경이다. 기존에는 "도구를 안 불렀다"는 **부재**로 읽었는데, 그러면 되묻는 문장만 얻고 **선택지를 만들 수 없다.** 도구를 둘로 나눠(`ask_followup` / `classify_and_refine`) **부족도 구조화된 신호**로 만들었다. `tool_choice: {"type":"any"}`로 반드시 하나를 부르게 강제한다.
- **카테고리 선택지**: 고정 목록 + 모델 제안을 합친다. **카테고리만은 모델 것을 무시하고 고정 7종을 쓴다** — `enum`으로 스키마에 박아도 표시 문구가 흔들리면 매칭이 깨진다.
- **"다음" 버튼의 정체**: 서버에 단계 전환 API가 없다. 칩을 누르는 것도 메시지 전송이다. **몇 단계가 될지는 모델이 정한다** — 첫 문장에 다 쓰면 되묻기 없이 확정안이 나온다.
- **아무말 대잔치**: 판정은 모델이 한다(자기가 뭘 물었는지 아니까 같은 `missing`으로 다시 되묻는다). 서버는 **같은 단계가 반복되는 횟수만 센다** — 2회면 예시를 붙이고 4회면 `409 CONVERSATION_STUCK`. 서버가 "3층이 위치로 충분한가"를 규칙으로 판단하려 들면 반드시 정상 입력을 막는다.
- **Redis↔DB 타이밍**: 기준은 하나 — *잃으면 사용자가 다시 만들어야 하는 것은 PostgreSQL*. **작업본 방식을 쓰지 않는다.** 여기 쌓이는 건 append-only 대화라 한 턴이 곧 확정이고, 미루면 새로고침에 사라진다. **나갈 때 저장하는 동작이 없다**(이미 저장돼 있다). Redis가 통째로 죽어도 민원과 대화는 안 사라진다.
- **Bedrock 호출 규격**: 실측 코드가 확인해준 제약 셋(리전 하드코딩 금지 · `global.` 프로필 필수 · 자격증명 코드 삽입 금지)을 명시. `invoke_model` + Anthropic 네이티브 포맷, `system`은 최상위 필드, `user`/`assistant` 교대 규칙과 **LLM 실패로 `user`가 연속됐을 때 합쳐 보내는 처리**까지.
- **계정 인증의 실제 수준을 솔직히 적었다** — 도메인이 등록됐는지만 보고 **그 이메일의 주인인지는 확인하지 않는다.** 데모 범위에서 이대로 가되, 실서비스면 이메일 인증이 필요하고 그때 막아야 하는 건 읽기가 아니라 쓰기라고 적었다.

**계약서는 1361 → 1303줄.** 줄 수는 비슷하지만 내용이 바뀌었다 — 구현이 빠지고 경계 설명이 들어갔다. 머리말에 "이 문서의 경계" 절을 넣어 무엇이 여기 있고 무엇이 `backend-design.md`에 있는지 표로 갈랐다.

## [2026-08-27] 세션 컨테이너를 v1 문서의 로직으로 정정
`chat_sessions` 테이블을 새로 설계했는데, **그 로직은 이미 `requirements_v1.md` §7.5에 정의돼 있었다.** 있는 것을 못 보고 다시 만든 것이라 원문 로직으로 갈아엎었다.

**세 겹이 흐르는 구조** — 현재대화(버퍼) → 차면 과거대화로 밀림 → 일정량 쌓이면 **이전 세션주제와 함께** 압축해 새 세션주제.

**핵심은 압축이 누적된다는 것이다.** 과거 대화를 요약할 때 이전 세션주제를 함께 넣는다.
```
새 세션주제 = 압축( 이전 세션주제 + 밀려난 과거 대화 )
```
이전 요약을 버리고 최근 것만 요약하면 세 번째 압축쯤에 초반 맥락이 증발한다. 내가 처음 쓴 설계에는 이 누적이 없었다.

**버퍼를 따로 저장하지 않는다.** 대화는 어차피 전부 DB에 있으므로 `compacted_upto`(압축 경계)만 기억하면 그 이후가 곧 버퍼다.

**세션주제는 PostgreSQL에 둔다.** LLM을 태워 만든 값이라 잃으면 비용을 다시 치러야 하고, 그 사이 맥락 없이 대화가 돈다. Redis에 두는 것은 압축 진행 표시(`compact:{sid}`)뿐이고 그건 잃어도 다음 턴에 다시 시도한다.

**압축은 턴 응답을 보낸 뒤 백그라운드로 돈다.** 실패해도 기존 값을 유지하고 다음 턴에 재시도한다 — 부가 작업이지 필수 경로가 아니다. 세션 단위로 `SET NX` 직렬화하는 이유는 압축과 다음 턴이 동시에 `compacted_upto`를 옮기면 구간이 겹치거나 비기 때문이다.

**최근 N턴은 압축하지 않는다.** 방금 오간 말이 요약으로 뭉개지면 되묻기가 이상해진다.

**제목은 압축이 함께 만든다.** 따로 호출하지 않는다. 사용자가 직접 정하면 `is_manual_title`로 잠겨 자동 갱신이 덮어쓰지 않는다.

**LLM 호출 시그니처를 바꿨다** — `refine(history)` → `refine(context, buffer)`. 세션주제는 `system`에, 버퍼는 `messages`에 넣는다. 압축된 맥락을 `messages`에 사용자 발화처럼 끼우면 모델이 그걸 학생이 방금 한 말로 읽는다.

실측 후 정할 값에 버퍼 크기·압축 임계치·압축용 모델을 추가했다.

## [2026-08-27] 백엔드 설계 적대적 검토 — 10건
`backend-design.md`를 통독하고 계약서와 교차 대조했다.

**문서 간 불일치 3건**

3. **§2 계층 규칙과 §11 예외가 모순.** "라우터가 repo를 직접 부르지 않는다"고 해놓고 "#1은 라우터에서 바로"라고 적었다. **예외를 없앴다** — "이건 간단하니까"가 쌓이면 규칙이 무너지고, 예외 없는 규칙이라야 테스트로 강제할 수 있다.

**설계 구멍 7건**
4. **`compacted_upto`가 개수인지 id인지 불명확했다.** 개수면 중간 삭제에 경계가 어긋난다. **메시지 id로 확정** — 단조 증가하므로 `WHERE id > compacted_upto`가 정확히 버퍼다.
5. **압축 중 새 턴이 들어오면 구간이 흔들렸다.** 압축 시작 시점에 `(from, to]`를 고정하고, 갱신 SQL에 `WHERE compacted_upto = from`을 걸어 **다른 압축이 먼저 끝났으면 이번 결과를 버린다.** 턴 락과 압축 락을 따로 둔 이유(압축이 대화를 막지 않는다)도 적었다.
6. **확정안이 압축 구간에 묻히면 모델이 처음부터 다시 묻는다.** 압축 프롬프트에 "확정된 항목은 그대로 옮겨 적어라"를 넣었다. 접수 자체는 `refined_json`을 DB에서 직접 읽으므로 무관하다.
7. **압축 LLM 호출이 `bedrock_logs`에 안 남았다.** 심사에서 호출 수를 보는데 정제만 세면 실제보다 적다. 압축 건도 남기되 `is_complete=false`.
8. **`tool_use` 블록이 여럿 올 때 처리가 없었다.** 첫 번째만 쓴다 — 둘을 합치려 들면 "부족한데 확정도 했다"는 모순 상태가 된다.
9. **칩이 Redis에만 있었다.** TTL 만료 후 새로고침하면 **대화는 멀쩡한데 선택지만 사라진다.** `complaint_conversations.choices JSONB`에 함께 저장하고 Redis는 캐시로 격하.
10. **`draft:{key}:owner`가 불필요해졌다.** `chat_sessions`에 `user_id`가 생긴 순간 소유권이 DB 사실이 됐는데 Redis 키가 남아 있었다. 두 곳에 있으면 어긋난다 — Redis 쪽을 없앴다. 초안이 키 하나로만 식별되던 시절의 잔재다.

부수로 `missing='detail'`인데 카테고리가 아직 없는 경우(모델이 순서를 안 지킬 수 있다), 커넥션을 LLM 호출 전에 반납하는 지점을 흐름도에 명시, 모듈명을 `draft_*` → `session_*`으로 정리했다.

## [2026-08-27] 적대적 검토 2차 — 6건
**데이터가 사라지는 문제 1건**
1. **탈퇴하면 접수된 민원의 근거 대화가 사라진다.** `chat_sessions`가 `users`에 CASCADE로 걸려 있고 대화가 세션에 매달려 있으면, 탈퇴 시 세션→대화가 연쇄 삭제된다. 그런데 `complaints`는 SET NULL이라 **민원은 남는다**(정본이 "학교의 공공 기록이라 보존"이라 명시). 결과적으로 **민원은 있는데 관리자 상세의 "학생 원문"이 비는** 상태가 된다.
   → **대화 행이 두 주인을 갖게 했다.** `chat_session_id`는 `SET NULL`, `complaint_id`는 `CASCADE`. 세션이 지워져도 대화는 민원에 매달려 남는다. 접수되면 두 FK가 모두 채워져 어느 쪽으로 찾아도 같은 행이 나온다. 조회 경로가 둘(작성 중엔 세션으로, 접수 후엔 민원으로)인 것도 여기서 자연스럽게 따라온다.

**문서 간 불일치 2건**
2. **대화 행의 정체가 문서마다 달랐다.** `.kiro`는 `draft_key CHAR(36)`, 백엔드는 `chat_session_id`, 그리고 `chat_sessions` 테이블 자체가 `.kiro`에 없었다. 세 문서를 `chat_sessions` + 두 FK 구조로 통일했다.
3. **새 오류 코드가 계약 표에 없었다.** `SESSION_CLOSED`·`CONVERSATION_STUCK`이 백엔드에만 있어 프론트가 분기할 근거가 없었다. 추가.

**설계 구멍 3건**
4. **빈 세션이 쌓인다.** `POST /chat-sessions`가 바로 행을 만들고 접수 때도 다음 세션을 미리 발급한다. 열어놓고 아무 말 안 하면 목록에 누적된다. → **메시지 없는 세션은 목록에서 빼고**, 정리 작업이 지우고, "새 대화"를 눌렀을 때 이미 빈 세션이 있으면 재사용한다(연타 방지).
5. **철회 후 세션 상태가 정의되지 않았다.** 다시 열어 쓸 수 있게 하면 "무엇이 접수됐던 것인지"가 흐려진다(관리자가 이미 봤을 수 있다). → **읽기 전용 유지.** 다만 목록에는 "철회됨"으로 남긴다 — 사라지면 자기가 뭘 냈었는지 모른다.
6. **`preview`가 어느 확정안인지 불명확.** 확정 후에도 대화를 이어가면 새 확정안이 나온다. → **항상 마지막 것.** 접수도 마지막을 쓰므로 화면과 결과가 어긋나지 않는다.

정리 작업 대상에 빈 세션과 고아 대화(두 FK가 모두 NULL)를 추가했다.
