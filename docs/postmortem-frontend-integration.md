# 사후 분석 — 프론트·백엔드 연동이 두 번 파괴된 건

_2026-08-29 · 대상: 팀 전원 · 상태: 원인 규명 완료, 재발 방지 미적용_

**증상**: 배포된 화면에서 챗봇이 열리지 않고, 민원 접수가 되지 않으며, 프로필이 비어 있고,
로그아웃을 눌러도 로그아웃되지 않았다. 게시판에는 아무도 쓴 적 없는 민원 5건이 떠 있었다.

**결론**: 백엔드에 연결돼 있던 프론트 코드가 브라우저 안에서 도는 목업으로 **두 번 덮어써졌다.**
버그가 아니라 머지 사고다. 그리고 목업에 박힌 폴백들이 그 사실을 화면에서 가렸다.

이 문서는 추측을 적지 않는다. 아래 표와 시간순은 전부 `git` 기록에서 확인한 것이다.

---

## 1. 무슨 일이 있었나

### 1.1 `ChatModal.jsx` 상태 추적

한 파일만 따라가면 전체가 보인다.

| 커밋 | 내용 | API 참조 | 목업 로직 |
|---|---|---|---|
| `c235c74` | 프론트엔드 초기 구조 · 전체 페이지 컴포넌트 | **3** | 0 |
| `b591b88` | 이미지첨부, UI통일, PC프레임, 그라디언트 | 0 | **5** |
| `2ea3818` | merge: resolve conflicts - keep frontend UI changes | 0 | 5 |
| `9020f23` | 프론트 전체 UI (랜딩/챗봇/상세/철회/페르소나/모션) | 0 | 5 |

*API 참조 = `createSession`·`api/session` 등장 횟수 / 목업 로직 = `guessCategory`·`processStep` 등장 횟수*

**`c235c74` 시점에 이미 백엔드에 연결돼 있었다.** UI 브랜치는 거기서 갈라져 나와 그 파일을
목업으로 **다시 썼다.** 없던 것을 만든 게 아니라 있던 연동을 지우고 브라우저 구현으로 바꾼 것이다.

### 1.2 시간순

```
20:15  c4bc63a  백엔드 연동 + 이미지 첨부 (Bedrock vision)
20:26  b591b88  UI 브랜치 — c235c74에서 분기. 연동을 목업으로 대체
20:30  2ea3818  merge "keep frontend UI changes"          → 연동 파괴 ①
20:54  48e58d9  연동 복구 (c4bc63a에서 되살림)
23:11  9020f23  UI 전면 개편 — 2ea3818 위에서 작업(이미 목업 상태)
23:20  3853913  merge — 충돌 마커를 그대로 커밋            → 빌드 파괴 ②
00:02  ec31971  충돌 해소 + 목업 제거 + 실제 API 연결
```

### 1.3 두 번째 파괴가 더 나빴던 이유

`9020f23`은 **`2ea3818` 위에서** 갈라졌다(`git merge-base 9020f23 48e58d9` → `2ea3818`).
즉 UI 작업자는 20:54의 복구(`48e58d9`)를 본 적이 없고, **이미 목업이 된 상태를 기준으로**
3,650줄을 새로 쌓았다.

그래서 머지할 때 복구된 파일마다 정확히 충돌이 났고, 그것을 **마커째 커밋**했다.

```
$ git grep -l -E "^<<<<<<< |^>>>>>>> " 3853913 -- src/frontend
ChatModal.jsx   BoardPage.jsx   ProfilePage.jsx   StatusPage.jsx     (충돌 블록 13개)
```

**원격 main에서 `npm run build`가 실패하는 상태였다.** 누가 pull 받아도 즉시 막힌다.

### 1.4 계약 파일은 아무도 건드리지 않았다

| UI 커밋 | `src/frontend/src/api/` 변경 |
|---|---|
| `7e90250` | 0개 |
| `b591b88` | 0개 |
| `408fd51` | 0개 |
| `9020f23` | 0개 |

계약(`api/*.js`)은 그대로 둔 채 **그것을 쓰는 쪽만** 갈아엎었다. 두 작업이 서로를 모르는 채
같은 파일에서 갈라진 구조적 이유가 여기 있다.

## 2. 왜 아무도 눈치채지 못했나 — 폴백이 실패를 가렸다

목업은 조각이 아니라 **완성된 평행 구현**이었다. 실패할 때마다 그럴듯한 화면으로 넘어갔다.

| 위치 | 코드 | 가린 것 |
|---|---|---|
| `AuthPage` | `catch { applyDemoUser() }` | 세션 없이 로그인된 것처럼 보임 |
| `AuthPage` | `if (selectedSchool === DEMO_SCHOOL) applyDemoUser()` | **가입 버튼이 `signup`을 한 번도 부르지 않음** |
| `AuthPage` | `listSchools().catch(() => [DEMO_SCHOOL])` | 학교 목록 장애가 안 보임 |
| `AppContext` | `rows.length ? rows : DEMO_COMPLAINTS` | 빈 게시판과 API 실패가 구분되지 않음 |
| `HomePage` | `complaints.length ? complaints : demoComplaints` | 지도 핀 5개가 항상 떠 있음 |

### 2.1 사용자가 본 증상과 실제 원인의 대응

| 증상 | 실제 원인 |
|---|---|
| 프로필의 이메일·소속 캠퍼스가 빈칸 | 그 화면은 **게스트 프로필**이었다. `user`가 `null` |
| 로그아웃을 눌러도 그대로 | `user=null`이면 `App`이 `<MainPage isGuest>`를 렌더 → 같은 앱 화면에 머묾 |
| 로그인했는데 세션이 없음 | `applyDemoUser`가 `setUser()`만 함. **쿠키도 Redis 세션도 만들지 않음** |
| 메인에 "군산대학교" | 게스트 홈의 `universities[0]`. 롤링은 게스트에서만 돌아 인덱스 0에 멈춤 |
| 게시판에 모르는 민원 5건 | `demoComplaints` |
| 가입 도메인이 `koreadae.ac.kr` | `DEMO_SCHOOL`이 입력 **초기값**이었다. DB에 없는 도메인 |
| 챗 화면이 안 뜨고 접수 불가 | `ChatModal` JSX가 미정의 변수 `busy` 참조 → 렌더 시 ReferenceError |

**화면은 항상 정상으로 보였다.** 그래서 "연동이 안 됨"이 아니라 "가끔 이상함"으로 보였고,
원인 규명이 늦어졌다.

## 3. 검증이 문제를 잡을 수 없는 위치에 있었다

| 도구 | 무엇을 보나 | 이번 건을 잡았나 |
|---|---|---|
| `npm run build` | 번들링만 | ✗ 스코프를 검사하지 않아 `busy`를 통과시킴 |
| 백엔드 `pytest` 40개 | 서버 안쪽 | ✗ 경계를 건너지 않음 |
| API 수동 검증(curl) | HTTP 경계 | ✗ 전부 통과했다. 죽은 건 브라우저 쪽 |

**경계를 검사하는 장치가 하나도 없었다.** 필드명이 `timestamp`인지 `created_at`인지,
프론트가 API를 부르기는 하는지 확인하는 것이 0이었다.

`npm run build`가 성공한다는 사실이 **아무것도 보증하지 않는다**는 점이 이번 건의 핵심 교훈이다.

## 4. 계약 위반 목록 (`docs/api-contract.md` 기준)

머지 사고와 별개로, 목업이 계약과 어긋나 있던 지점들이다. `ec31971`에서 전부 정정했다.

### 4.1 필드명

| 프론트가 읽던 이름 | 백엔드가 주는 이름 |
|---|---|
| `c.timestamp` | `created_at` (ISO 8601) |
| `c.rawText` / `c.summary` | `body` |
| `complaint.comment` (단수) | `comments[]` (배열) |
| `user.schoolName` | `school_name` |

→ `AppContext.normalize()` 한 곳에서 별칭을 붙여 흡수했다. 호출부는 건드리지 않았다.

### 4.2 존재하지 않는 함수 호출 (실행 시 크래시)

| 호출 | 실제 계약 |
|---|---|
| `addComplaint(...)` | `POST /chat-sessions/{sid}/submit` |
| `changeStatus(id, status)` | accept / resolve / hold / reject **4개로 분리** |
| `deleteComplaint(id)` | `POST /complaints/{id}/withdraw` (+ `verify-password`) |
| `handleAdminVerify()` | 계약에 없었음 → §5에서 신설 |

### 4.3 상태 전이표 불일치

| 목업 | 백엔드 실제 |
|---|---|
| `미확인 → ['확인']` 버튼 | 버튼이 아니라 **열람(POST open)의 부작용** |
| `보류 → ['확인','처리중']` | 존재하지 않는 전이 (409) |
| `처리중 → 해결완료`만 | `처리중` **및 `보류`** → 해결완료 |

### 4.4 필수 입력 누락

- **거절 사유**: 입력 UI 자체가 없었다 (서버는 422)
- **보류 사유**: 비면 토스트만 띄우고 전송
- **철회**: `confirm()` 1회, 비밀번호 없음 → 정본은 3단계 (①비밀번호 ②최종확인 ③실행)

## 5. 되살린 기능 — 교직원 인증

`ProfilePage`의 "교직원 / 관리자 인증"은 백엔드에 대응 엔드포인트가 없었고,
`isAdmin`·`adminCode`·`handleAdminVerify`가 정의되지 않은 채 붙어 있었다.

**한 번은 이것을 UI째 삭제했다. 잘못된 판단이었다** — 삭제는 최소변경이 아니라 기능 제거다.
`ec31971`에서 복원하고 백엔드를 새로 만들어 연결했다.

```
POST /auth/admin-code   { admin_code }  →  200 Me
```

| 계층 | 추가 |
|---|---|
| `repo/user_repo.py` | `get_school_id()`, `set_role()` |
| `services/auth_service.py` | `promote_with_admin_code(user_id, code)` |
| `schemas/auth.py` | `AdminCodeIn` |
| `routes/auth.py` | `POST /auth/admin-code` |

설계상 주의점 둘:

1. **코드 대조를 그 계정의 소속 학교로 한정한다.** 다른 학교 코드로 승격되면 학교 격리가 뚫린다.
2. **역할은 Redis 세션에도 박혀 있다.** DB만 바꾸면 다음 요청이 여전히 `student`로 판정된다.
   그래서 옛 세션을 지우고 새 role로 재발급한 뒤 쿠키를 갈아끼운다.

## 6. 재발 방지 (미적용 — 합의 필요)

| # | 조치 | 이번 건에서 무엇을 잡았을까 |
|---|---|---|
| 1 | **충돌 마커 pre-commit 훅** — `git grep -E '^<<<<<<< '` 걸리면 커밋 거부 | `3853913` 자체를 막았다 |
| 2 | **AST 스코프 검사를 빌드 뒤에** — 미정의 참조 검출 (30줄이면 된다) | `busy` → 챗 화면 사망 |
| 3 | **폴백 금지 규칙** — `catch → 데모` 대신 에러 표시 | 목업이 실패를 가리는 구조 자체 |
| 4 | **연동 CI** — `src/api/` 밖에서 `fetch` 사용 금지, 페이지가 api 모듈을 하나도 import하지 않으면 실패 | 목업 재유입 |
| 5 | **머지에서 "한쪽 통째 채택" 금지** | 연동 파괴 ①·② 둘 다 |

### 6.1 구조적 조치

1~4는 도구로 막을 수 있지만, 근본은 **UI 담당과 연동 담당이 같은 파일을 다시 쓰는 구조**다.
`ChatModal.jsx` 하나를 두 사람이 각자 처음부터 작성했고, 머지 때마다 한쪽이 통째로 죽었다.

`docs/team-split.md`는 백엔드를 디렉토리 단위로 갈랐지만 **프론트에는 그런 경계가 없다.**
프론트도 같은 방식이 필요하다 — 예를 들어 컴포넌트는 UI 담당이, `api/`와 `store/`는 연동
담당이 소유하고, 컴포넌트에서 데이터가 필요하면 `store/`의 훅을 부르게 한다. 그러면 UI 개편이
연동 코드를 건드릴 일이 없다.

## 7. 이번 대응에서 내가 잘못한 것

기록으로 남긴다. 같은 실수를 반복하지 않기 위해서다.

1. **교직원 인증을 연결하지 않고 삭제했다** (§5). "최소변경"을 삭제로 해석했다.
2. **게스트 홈을 `LandingPage`로 교체해 캠퍼스 지도를 없앴다.** 로그아웃 버그를 고치려다
   멀쩡한 UI를 날렸다. 되돌린 뒤 게스트 모드 자체를 제거하는 쪽으로 다시 정리했다.
3. **충돌 해소 중 구버전 한 줄(`busy`)을 새 UI에 섞어 넣고 그대로 배포했다.**
   빌드가 통과했다는 이유로 믿었다.
4. **API 레벨 검증만 하고 "ALL PASS"라고 보고했다.** curl로 두드린 것은 전부 통과했지만
   실제 화면은 죽어 있었다. 닿을 수 있는 층만 확인하고 기능이 동작한다고 말한 것이다.
   **브라우저에서 렌더되는 것을 확인하기 전까지 "동작한다"고 쓰지 않는다.**
